# 워킹 프로토타입을 위한 백엔드 팔: 조사와 제안

2026년 11월 14일. 여덟 영역을 서브에이전트가 따로 조사했고(각 보고서는 `2026-11-14-backend-arms/`에 출처와 함께 있다), 이 글은 그것을 하나로 묶은 것이다. 조사는 문서를 읽은 것이고, 이 Mac에서 띄워 본 것은 아직 없다.

## 결론

- **지금 스튜디오는 목업을 지으라고 시킨다.** 초안 지시문이 "백엔드는 아직 없다, JSON 픽스처를 써라"고 말하고, 검증은 화면이 뜨는지와 보기 좋은지만 본다. 워킹 프로토타입이 되려면 셋이 함께 바뀌어야 한다: 프로젝트마다 실제 백엔드, 가입과 로그인과 사용자 시나리오가 든 화면설계서, 그 시나리오를 스튜디오가 직접 돌려 보는 검증.
- **기본 팔은 Supabase 한 벌이다, 프로젝트마다.** DB, 인증(Google과 Kakao가 내장), 파일, 실시간(채팅), 서버 함수, 예약 작업, 메일 캡처가 한 벌에 들어 있다. 여덟 영역이 서로 모르는 채 같은 결론에 닿았다.
- **Redis는 기본이 아니다.** Postgres가 큐와 예약과 실시간을 이미 한다. 필요한 제품에만 붙이는 선택 팔로 두고, 붙일 때는 Valkey를 쓴다(Redis는 라이선스가 바뀌었다).
- **결제, 본인인증, 문자, 지도, 푸시는 띄울 서비스가 없다.** 전부 남의 서비스다. 키가 없을 때는 호스트 게이트웨이의 대역이 흐름을 끝까지 돌리고, 키가 들어오면 그대로 통과시킨다. 스튜디오에 이미 있는 방식이다.
- **앞설 자리가 있다.** 상용 빌더 가운데 "가입하고, 저장하고, 재시작한 뒤에도 남아 있다"를 사람 손 없이 확인하는 곳은 찾지 못했다.

## 워킹 프로토타입의 계약

스튜디오가 직접 실행해서 확인하고, 통과하지 못하면 돌려보내는 것:

1. **가입하고 로그인한다.** 테스트 사용자가 이메일로 가입하고(확인 메일은 로컬 메일함에서 읽는다) 로그인한다.
2. **남는다.** 핵심 과업을 하고 새로고침한 뒤에도, 백엔드를 재시작한 뒤에도 데이터가 있다.
3. **남의 것은 보이지 않는다.** 사용자 A의 행을 사용자 B와 로그인하지 않은 사람이 읽지 못한다. 클라이언트에 실리는 코드에 관리자 키가 없다.
4. **같이 쓰는 제품이면 서로 보인다.** A가 바꾼 것이 B의 화면에 나타난다.
5. **화면설계서의 시나리오가 끝까지 걸어진다.**

3번을 넣은 까닭: 다른 빌더의 사고가 대부분 여기서 났다. 한 조사에서 Lovable로 만든 앱 1,645개 가운데 170개가 데이터를 내주고 있었고, 그때의 검사는 접근 정책이 "있는지"만 봤다.

## 팔 목록

팔 하나는 다섯 가지의 묶음이다: 로컬에서 도는 서비스, 프로젝트에 주입되는 환경변수, 클라이언트 코드, 시드 데이터, 그리고 그것이 되는지 확인하는 시나리오. 프로젝트는 필요한 팔만 선언한다.

| 팔 | 무엇을 주나 | 로컬에서 도는 것 | 키 없이 | 소유자가 발급할 것 |
|---|---|---|---|---|
| **기본** | DB, 이메일 가입과 로그인, 파일, 실시간, 서버 함수, 예약 작업, 메일 캡처 | Supabase 로컬 스택, 프로젝트마다 한 벌 | 전부 된다 | 없음 |
| **소셜 로그인** | Google, Kakao, Naver, Apple | 기본 팔의 인증 + 같은 흐름을 타는 대역 로그인 | 대역 로그인(개발용이라고 표시) | Google OAuth 클라이언트, Kakao 앱, Apple은 유료 개발자 계정 |
| **채팅 · 실시간** | 1:1과 그룹 채팅, 입력 중, 접속 표시, 함께 보는 목록 | 기본 팔의 실시간 + 메시지 테이블 | 전부 된다 | 없음 |
| **알림** | 앱 안의 알림함, 푸시 | 알림함은 기본 팔, 푸시는 게이트웨이 대역 | 알림함과 웹 푸시 | Expo 프로젝트 ID, FCM, iOS는 유료 Apple 계정 |
| **검색** | 한국어 검색 | 기본 팔의 PGroonga | 된다 | 없음 |
| **작업** | 큐, 예약 | 기본 팔의 큐와 크론 | 된다 | 없음 |
| **키-값** (선택) | 몇 분 안에 사라지는 값, 빠른 카운터, 읽기까지 막는 속도 제한, 남의 API 응답 캐시 | Valkey 컨테이너 하나 | 된다 | 없음 |
| **결제** | 승인, 취소, 실패 | 게이트웨이 대역 | 대역 | Toss Payments 테스트 키(개인 가입으로 된다). 실결제는 사업자 |
| **본인인증** | 실명 확인 | 게이트웨이 대역 | 대역 | PortOne의 KCP 테스트 채널. 실사용은 사업자 |
| **문자 · 알림톡** | 인증번호, 안내 | 대역(보낸 메시지함에 쌓인다) | 대역 | Solapi에 본인 번호 등록. 알림톡은 사업자 |
| **지도 · 주소** | 지도, 장소, 우편번호 | 없음(남의 서비스) | 우편번호는 키 없이 된다 | Kakao Developers 앱(지도 켜기, 도메인 등록) |
| **인앱 결제** | 구독, 구매 | 대역 | RevenueCat Test Store | 스토어 계정 |
| **AI** | 모델 호출, 스트리밍 | 호스트 게이트웨이(이미 있다) | 흉내 낸 스트림 | 구독이나 키 |
| **오류 수집** (선택) | 오류 추적 | GlitchTip 컨테이너, 또는 게이트웨이가 받아 적기 | 된다 | 배포할 때 Sentry |
| **음성 · 영상** (선택) | 통화 | LiveKit 개발 모드 | 된다 | 없음 |

넣지 않기로 한 것과 까닭:

- **공유 Supabase 하나에 프로젝트별 스키마.** 사용자와 키와 파일이 섞인다. 자가 호스팅 Supabase는 프로젝트 하나를 흉내 내는 구조다.
- **PocketBase.** 가장 가볍지만 한 사람의 프로젝트이고 1.0 이전이다.
- **Clerk, Firebase 인증.** 로컬에서만 돌릴 수 없다.
- **호스팅 채팅 서비스(Stream, Sendbird).** 키 없이 띄울 수 없고 무료 한도가 작다.
- **Socket.IO로 직접 짓는 채팅.** 엔진이 인증과 기록과 접속 표시를 매번 새로 짜게 되어 틀릴 곳이 늘어난다.
- **MinIO.** 저장소가 보관 처리됐다. 파일은 기본 팔이 한다.

## Redis를 언제 붙이나

엔진이 따를 규칙으로 적으면:

1. 기본은 Postgres다. 메일과 푸시와 썸네일의 재시도는 큐, 예약과 정리는 크론, 채팅과 입력 중과 접속 표시는 실시간, 세션은 인증, 순위는 인덱스와 정렬.
2. 다음 가운데 하나가 있으면 Valkey를 붙인다: 몇 분 안에 사라져야 하는 값(인증번호, 임시 잠금), 초당 여러 번 바뀌는 카운터나 실시간 순위, 읽기 요청까지 막아야 하는 속도 제한, 느리거나 돈이 드는 남의 API 응답의 캐시.
3. 원본 데이터는 Valkey에 두지 않는다. 지워져도 Postgres에서 다시 만들 수 있어야 한다.

## 로그인: 키가 없을 때와 있을 때

**키가 없을 때.** 이메일 가입과 매직 링크와 전화 인증번호(고정 코드)는 로컬에서 끝까지 된다. Google과 Kakao는 진짜 키 없이는 되지 않으므로 대역 로그인을 둔다: 인증 서비스 옆에 가짜 로그인 서버를 띄워 같은 OAuth 흐름과 같은 콜백을 탄다. Kakao는 인증 서비스에 주소를 바꾸는 설정이 있어 제공자 이름까지 운영과 같게 둘 수 있다. 화면에는 개발용이라고 표시한다.

**키가 있을 때 소유자가 할 일.**

- **Kakao**: Kakao Developers에서 앱 만들기 → REST API 키 → 클라이언트 시크릿 켜기 → 카카오 로그인 켜기 → 리다이렉트 주소 등록(완전히 일치해야 하고 열 개까지) → 동의 항목. 이메일은 비즈 앱만 받을 수 있어서, 아니면 이메일 없는 사용자를 허용한다.
- **Google**: OAuth 클라이언트 만들기. 웹과 iOS와 Android가 따로이고 Android는 서명 지문이 필요하다.
- **Apple**: 유료 개발자 계정. 다른 소셜 로그인을 넣으면 App Store 규정상 Apple 로그인도 넣어야 하고, 계정 삭제 기능도 있어야 한다.

**Expo에서.** 브라우저 방식의 로그인을 기본으로 한다. 웹과 개발 빌드에서 한 코드로 된다. 네이티브 Kakao와 Google SDK는 개발 빌드가 생긴 뒤의 일이다.

## 화면설계서

지금의 화면 명세는 화면과 상태와 핵심 과업을 담는다. 여기에 넣을 것:

- **역할**: 누가 쓰는가(총무와 회원처럼), 각자 무엇을 보고 무엇을 할 수 있는가.
- **들어오는 길**: 가입, 로그인, 로그아웃, 세션이 끊겼을 때, 비밀번호를 잊었을 때, 탈퇴.
- **시나리오**: 사용자가 처음 와서 목적을 이루기까지를 번호 붙은 걸음으로. 걸음마다 어느 화면의 어느 상태인지.
- **남는 것**: 걸음마다 무엇이 어디에 저장되는가.

시나리오가 곧 검증의 대본이 된다(계약 5번). 문서를 따로 하나 더 만들지 않고 화면 명세를 넓혀 사람이 읽는 화면설계서로 내는 쪽을 권한다. 초안 트랙도 짧은 판은 쓴다.

## 폰 앱에서 되는 것과 안 되는 것

- **컨테이너의 웹 타깃에서 자동으로 확인되는 것**: 가입과 로그인, 새로고침 뒤의 세션, 데이터와 실시간, 파일 올리기, 서체, 오프라인 캐시.
- **시뮬레이터나 기기가 있어야 하는 것**: 푸시, 네이티브 로그인 SDK, 보안 저장소, 딥 링크, 카메라, 지도.
- **기기의 서체**: 지금 프로젝트에 넣는 woff2는 웹에서만 된다. Android는 받지 않고, 지원하지 않는 형식은 앱을 죽일 수 있다. 기기에는 TTF나 OTF를 넣어야 한다.

## 무게와 모르는 것

- **메모리.** Supabase의 기본 방식은 쉬고 있을 때에도 프로젝트마다 약 2.6GiB를 쓴다. 명령줄 도구의 새 방식(필요한 서비스만 깨우고 쉬면 재운다)은 약 290MiB다. 둘 다 Supabase가 직접 잰 값이고, 이 Mac에서 재야 한다. 새 방식은 아직 공개 알파다.
- **대역 로그인이 로컬 스택에서 되는가.** 사용자 정의 제공자와 Kakao 주소 설정이 로컬 명령줄 스택에서 먹는지 확인하지 못했다.
- **주소.** 브라우저에서 보는 주소와 프로젝트 컨테이너 안에서 보는 주소가 다를 것이다. 둘을 따로 넣어 줘야 할 수 있다.
- **Kakao가 localhost 리다이렉트를 받는가.** Supabase 문서의 안내로만 봤다.
- **마이그레이션은 되돌릴 수 없다.** 코드를 되돌려도 DB는 돌아오지 않는다. 엔진이 스키마를 바꾸기 전에 스냅샷을 뜨는 단계가 필요하다.

## 순서

1. **재기.** 이 Mac에서 Supabase 한 벌을 새 방식으로 띄워 메모리와 시작 시간과 프로젝트 컨테이너에서의 접근을 잰다. 안 되면 기본 방식으로, 쓰는 프로젝트만 띄운다.
2. **기본 팔.** 프로젝트가 팔을 선언하면 스튜디오가 띄우고, 환경변수를 넣고, 시드를 채우고, 스키마를 바꾸기 전에 스냅샷을 뜬다. 클라이언트 코드는 키트로 준다.
3. **화면설계서.** 화면 명세를 넓히고, 지시문에서 "백엔드는 아직 없다"를 걷어 낸다.
4. **검증.** 계약의 다섯 줄을 도는 시나리오 러너.
5. **증명.** 회비 장부를 워킹 프로토타입으로 다시 짓는다: 총무와 회원이 각자 가입하고, 총무가 올린 영수증이 회원에게 보이고, 재시작 뒤에도 남아 있다.
6. 그다음 소셜 로그인의 대역과 실제 키, 채팅, 한국 연동의 대역들.

## 소유자가 정할 것

- 계약의 다섯 줄이 워킹 프로토타입의 뜻으로 맞는가.
- Kakao와 Google의 개발자 콘솔에 앱을 지금 만들 것인가, 대역으로 먼저 갈 것인가.
- 사업자 등록이 있는가. 실결제와 알림톡을 어디까지 볼 수 있는지가 여기서 갈린다.
- 기기 쪽 확인을 iOS 시뮬레이터까지 넣을 것인가.
