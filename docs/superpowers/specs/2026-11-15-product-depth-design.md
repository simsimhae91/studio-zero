# 제품 깊이: 설계

2026-11-15. 소유자의 말: "개발되는 서비스의 깊이가 부족한 느낌임. 한두 페이지로 끝나는 느낌. 스튜디오로 구현되는 서비스는 실제 프러덕션 수준으로 나오는 것. 기능도 UI도." 예로 든 것은 다이어트 배틀 앱의 매칭, 사진으로 칼로리 계산, 헬스키트 연동, 랭킹, 팁, 승패 애니메이션, 식단·운동 추천이다.

## 1. 왜 얕은가 (잰 것)

- **지어진 제품의 크기.** 이 Mac에서 끝까지 간 두 제품: `lab-dues-works`는 화면 6개, 앱 코드 1,988줄, 테이블 4개, 시나리오 2개. `money-lab`은 화면 5개, 2,467줄, 테이블 2개, 시나리오 1개.
- **지시가 그렇게 말한다.** 초안 지시문(`DRAFT_BRIEF`)은 "가입과 로그인을 짓고, 아이디어를 담은 **화면 하나**를 다른 화면보다 먼저 끝까지" 지으라고 한다. 화면설계서의 `tasks`는 "핵심 흐름 1~5가지, 모든 기능이 아니라"이고 시나리오는 여섯까지("역할마다 하나")다. 계획 프롬프트는 "아무도 청하지 않은 일을 덧붙이지 말라"고 한다.
- **넓이를 묻는 자리가 없다.** 기능의 폭은 소유자의 한 문장에서만 온다. "이런 종류의 실제 제품에는 무엇이 있는가"를 묻는 단계가 없다.
- **이어 가는 것이 없다.** 첫 빌드가 끝나면 다음 기능은 소유자가 하나씩 떠올려 적어야 한다.
- **확인이 계획만큼만 간다.** 시나리오 게이트는 설계서의 시나리오를 걷는다. 얇은 설계서는 얇게 통과한다.
- **안쪽 화면은 아무도 재지 않는다.** 시각 감사와 초안 측정은 로그인하지 않은 채 경로를 연다. 계정이 있는 제품에서 재는 것은 들어가는 화면뿐이다.
- **한 번에 넓게는 해 봤고 실패했다.** 2026-11-13의 다이어트 매치: 한 엔진이 한 차례에 MVP 전체(파일 46개, 49분)를 지었고, 핵심 흐름 3개 중 1개만 걸어졌고, 감사는 F였다. 그 뒤 스튜디오는 "한 화면이라도 실제로 도는 것"으로 좁혔다. 지금의 얕음은 그 결정의 다른 면이다.

## 2. 원칙

넓게 계획하고, 조각마다 끝까지 짓고, 조각마다 걸어 본다. 넓이는 계획에서 오고, 깊이는 조각을 줄이지 않는 데서 온다. 검증 없이 넓히지 않는다.

## 3. 짓는 것

### 3.1 제품 지도 (`docs/product.json`)

빌드 전에 데몬이 모델에게 묻는다: 이 요청이 가리키는 종류의 실제 제품은 무엇으로 이루어지는가. 답은 구조화된 지도다.

```
pitch       한 문장
category    어떤 종류의 제품이고 어떤 실제 제품들 옆에 놓이는가
pillars     이 제품이 잘해야 하는 것 3~5가지
features[]  { id, name, why, tier: core|expected|delight,
              does[]: 사람이 할 수 있는 일과 보게 되는 것 (2~6줄),
              screens[]: 필요한 화면 이름,
              needs: { data[], device[], ai, external[] },
              inPreview: real | simulated | device-only, simulation }
milestones[] { id, name, goal, features[], acceptance[] }
```

- 소유자가 이름 붙인 기능은 바닥이지 천장이 아니다. 지도는 그 종류의 제품이 당연히 갖는 것(온보딩, 기록, 설정, 알림함 같은 것)까지 채운다.
- **검사는 데몬 코드가 한다**(`product/ProductMap.ts`): 기능 6개 이상, 모든 기능이 정확히 한 마일스톤에, 마일스톤 3~12개, 마일스톤 하나에 기능 4개까지(엔진이 한 차례에 끝낼 조각), 첫 마일스톤에 `core` 기능이 있을 것, 기능마다 `does` 2줄 이상, 마일스톤마다 `acceptance` 1줄 이상, `simulated`면 `simulation`에 무엇이 대신하는지. 걸리면 무엇이 틀렸는지와 함께 한 번 돌려보낸다.
- **될 수 있는 것과 없는 것을 지도가 말한다.** 프리뷰는 브라우저다. 카메라는 사진 고르기로 실제로 되고, 헬스키트와 푸시는 기기에서만 된다. 모델이 필요한 기능(사진으로 칼로리)은 소유자가 연결한 외부 API가 있을 때만 `real`이다. 아니면 `simulated`이고, 무엇이 대신하는지와 실제로 만들려면 무엇을 연결해야 하는지를 적는다. 스튜디오는 소유자의 구독을 제품의 사용자에게 내주지 않는다.
- 지도는 `docs/product.md`로도 렌더되어 소유자가 읽는다. 렌더는 코드가 한다.

### 3.2 로드맵 실행 (`app/RoadmapRunner.ts`)

지도의 마일스톤을 하나씩 태스크로 만들어 차례로 돌린다. 프로젝트당 로드맵 하나.

- 마일스톤 하나 = `build` 태스크 하나, 초안 트랙(컴파일, 스모크, 시나리오), 지시문은 `MILESTONE_BRIEF`.
- 통과하면 **합치고**(소유자가 시작할 때 정한다, 기본은 합침) 다음 마일스톤을 합쳐진 `main`에서 시작한다. 합칠 때마다 체크포인트가 있고, 합치지 않기로 하면 앞 태스크의 브랜치에서 이어 간다.
- 실패하면 거기서 멈추고 알린다. 다시 실행하면 그 마일스톤을 실패한 브랜치에서 이어 짓는다.
- 사용 한도에 걸리면 태스크가 기다렸다가 이어 간다(어제 넣은 한도 대기). 데몬이 다시 떠도 로드맵은 DB에 있고 이어진다.
- 로드맵을 시작하고 멈추는 것은 소유자만 한다(`roadmap.configure`). 유료 작업 여러 건을 줄 세우는 일이라 예약과 같은 규칙이다. 상한: 마일스톤 12개, 태스크마다 기존 토큰 예산.

### 3.3 마일스톤 지시문

엔진이 받는 것: 지도 전체는 저장소의 `docs/product.json`에, 이번 마일스톤의 기능(하는 일, 화면, 필요한 것, 프리뷰에서의 상태)과 이미 지어진 것, 나중 것은 요청문에. 규칙은 상수 `MILESTONE_BRIEF`:

- 화면설계서를 **넓힌다**: 이번 기능의 화면과 데이터를 더하고, 기능마다 시나리오 하나를 `"feature": "<id>"`로 표시해 더한다. 앞 마일스톤의 것은 지우지 않는다.
- 기능은 탐색에서 닿고, 백엔드에 쓰고 읽고, 비었을 때·불러올 때·실패했을 때가 있고, 그 기능의 순간(매칭이 잡히는 때, 이기고 지는 때)에 움직임이 있다. "준비 중" 화면은 기능이 아니다.
- `simulated` 기능은 어댑터 모듈 하나(`src/capabilities/<이름>`) 뒤에 두고, 실제 구현이 들어갈 자리를 적고, 화면에서 예시 값임을 밝힌다.
- 마이그레이션은 새 파일로만 더한다.

### 3.4 깊이 게이트

1. **기능마다 걸어 본다.** 화면설계서의 시나리오에 `feature`가 생긴다. 지금까지 지은 마일스톤의 모든 기능에 그것을 걷는 시나리오가 있어야 한다(`product/coverage.ts`, 코드가 센다). 없으면 그 기능 이름과 함께 돌려보낸다. 시나리오 게이트는 설계서의 시나리오를 전부 걸으므로, 마일스톤이 쌓일수록 앞의 기능도 다시 걸어진다.
2. **로드맵 제품의 설계서는 넓어도 된다.** 시나리오 상한 6은 "첫 버전" 기준이다. 제품 지도가 있는 프로젝트에서는 30.
3. **걷는 김에 잰다.** 시나리오를 걷는 브라우저는 가입한 사람으로 안쪽 화면에 서 있다. 걸음이 끝난 화면마다 폰 크기에서 DOM 검사(대비, 누름 크기, 넘침, 글자, 짜임)를 돌리고 화면을 찍는다. 화면 id마다 한 번. 블로커와 주요 결함은 **한 번** 돌려보내고, 그래도 남으면 통과시키되 로드맵에 빚으로 적는다(마지막 다듬기 마일스톤의 일감). 찍은 화면은 소유자가 보는 로드맵에 붙는다.

### 3.5 소유자가 보는 것

- 명령줄: `sz roadmap plan <프로젝트> "<요청>"`, `sz roadmap show <프로젝트>`, `sz roadmap run <프로젝트> [--no-merge]`, `sz roadmap stop <프로젝트>`.
- RPC `roadmap.get · plan · run · stop`, 이벤트 `roadmap.changed`, 폰 알림(마일스톤 통과, 멈춤, 끝).
- 데스크톱: 작업공간의 **로드맵** 탭. 마일스톤과 기능, 상태, 프리뷰에서 실제인지 예시인지, 찍힌 화면. 이 탭은 스튜디오 자신의 저장소에 카드로 지어 붙인다(데몬 계약이 먼저다).

## 4. 짓지 않는 것 (이번에)

- 지도를 웹 조사로 받치는 것. 모델이 아는 범위에서 쓰고, 조사는 다음에 붙인다.
- 소유자의 키 없이 도는 제품 속 AI. 키를 연결하면(`외부 API`) 실제가 되고, 없으면 예시다.
- 기기 빌드(헬스키트, 푸시). 어댑터와 프리뷰의 예시 데이터까지다.
- 마일스톤마다 다른 회사 모델의 디자인 심사. 측정은 매번, 심사는 소유자가 "검증까지"로 따로 돌린다.

## 5. 확인하는 법

- 단위: 지도 검사(틀린 지도마다 무엇을 말하는가), 커버리지, 지시문 조립, 설계서 상한.
- 흐름: 스크립트된 모델과 엔진으로 로드맵 한 벌(지도 → 마일스톤 1 → 합침 → 2 → 끝), 실패에서 멈춤, 다시 실행하면 실패한 브랜치에서, 재시작 뒤 이어 감, 에이전트는 시작하지 못함.
- 걷는 김에 재기: 실제 Chrome에서 결함이 있는 화면과 없는 화면.
- **실제 실행**: 새 프로젝트에 소유자의 예(다이어트 배틀)를 넣어 지도를 만들고 끝까지 돌린다. 본다: 마일스톤마다 통과했는가, 기능 몇 개와 화면 몇 개가 실제로 걸어졌는가, 예시로 남은 것은 무엇인가. 전과 견준다(화면 5~6개, 시나리오 1~2개).
