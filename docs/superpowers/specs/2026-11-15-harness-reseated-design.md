# 다시 앉힌 하네스: 증명하는 스튜디오

2026-11-15. 소유자의 말: "나는 이걸로 돈을 벌고싶은데. 지금 엣지가 부족해. 컨테이너에서 하는걸 뜯어고쳐도 됨. 모든 규칙은 의미가 없음(다시 써도 된다는 얘기). 앱만 할것도 아니고 웹만 할것도 아님 그냥서비스. 게임도 만들고 맥앱도 윈도우앱도 만드는건데. 하던 프로젝트를 이어가는것도 어렵고 적당히가 뭔지 모름. 개쩌는 하네스를 만드는게 목적. tauri 앱은 나중에 만들어도 되고 claude code로만 해도 괜찮음." 같은 날 "시간제한은 제거합니다."

이 문서는 그 말에 대한 답이다: 무엇을 버리고, 무엇을 남기고, 무엇을 새로 짓는가.

## 오늘 확인한 사실

**우리 쪽 (실제 실행).**
- 들여온 제품(credeal, Expo 네이티브 앱)을 스튜디오가 다루게 하는 데 27분, 191만 토큰이 들었고, 그러고도 볼 수 있는 것은 웹 화면뿐이었다. 그 제품에는 Maestro 흐름 44개가 이미 있었다. 같은 날 호스트에서 그 흐름 하나를 iOS 시뮬레이터에 돌리는 데 1분 47초, 토큰 0이 들었다.
- 걷기는 남의 제품을 집의 규칙으로 재서 "결함" 68건을 적었다. 대부분 그 제품의 서체와 간격이 우리 것이 아니라는 말이었다.
- 한 시간 넘게 일하던 만들기는 스튜디오의 시계에 죽었고, 이유는 엉뚱하게 적혔다.
- 엔진은 자기 도구를 뺏긴 채(스튜디오의 도구만) 라운드마다 새 프로세스로 뜨고 직전 답 4,000자만 넘겨받는다. 같은 모델이 Claude Code 안에서 하는 것보다 약하게 일한다.

**밖 (2026-11-15에 1차 자료로 확인. 수치는 대부분 한 번의 실행을 저자가 보고한 것).**
- 오래 도는 자율 개발에서 증거가 가장 강한 것: 에이전트가 고칠 수 없는 기계 검증 기준(오라클), 그다음이 깨끗한 맥락의 별도 검증자, 그다음이 파일에 남는 상태(명세, 기능 목록, 진행 기록). 만든 쪽이 자기 일을 채점하는 것은 모든 자료가 꼽는 실패다.
- 절차는 값이 든다. Anthropic의 실험에서 계획자+생성자+평가자 하네스는 혼자 도는 것의 20배였다($200 대 $9). "지금 모델이 혼자서는 안정적으로 못 하는 일일 때만 값을 한다." 모델이 좋아질 때마다 하네스 부품을 하나씩 빼야 했다.
- 오케스트레이션 배관은 모델 회사가 흡수했다: Claude Code에 플러그인(스킬, 서브에이전트, 훅, 워크플로, CLI), 백그라운드 세션과 감독자, worktree, `/goal`, 클라우드 프로젝트가 있다. 독립 오케스트레이터 앱(Conductor, Vibe Kanban, Terragon, Crystal)은 인수되거나 문을 닫았다.
- 사용자들이 아직 못 풀었다고 말하는 것: 속일 수 없는 완료 증명, 빨리 읽히는 검토, 취향, 작업 크기에 안 맞는 무거운 절차, 긴 작업에서의 표류, 비용.
- 브라우저 밖 검증은 도구가 다 있다: iOS는 simctl + Maestro + agent-device/MobileBuildMCP, Android는 Android CLI, macOS는 XCUITest/Peekaboo(VM 안에서), Windows는 GitHub Windows 러너 + winapp, 게임은 상태 훅 + 시간 전진(웹), GUT(Godot), PlayMode 테스트(Unity). 비전 모델은 미묘한 시각 결함을 잘 못 본다(최고 모델이 CSS 변화의 40%): 판정은 접근성 트리와 상태로 하고, 화면은 소유자에게 보이는 증거로 쓴다.

## 판단

스튜디오의 전제는 "엔진을 믿지 말고 가두고 관문으로 막는다"였다. 그래서 스튜디오의 천장은 가둔 엔진의 천장이고, 그것은 맨 Claude Code보다 낮다. 가장 센 에이전트를 약하게 만드는 우리에서는 엣지가 나오지 않는다. 엣지는 맨 도구에 없는 것에서 나온다.

맨 도구에 없는 것, 그리고 1년 동안 실제로 쌓은 것이 겹치는 자리는 하나다: **만든 것을 직접 써 보고, 됐다는 것을 증거로 보여 주는 일.** 걷기, 화면 측정, 필름스트립, 디자인 핸드북, 화면 계획이 전부 그 일의 재료였다. 틀렸던 것은 그 재료를 컨테이너 안의 관문으로, 한 가지 형식으로, 웹에만 묶은 것이다.

그래서: **스튜디오를 Claude Code 위로 옮겨 앉힌다.** 배관(작업 공간, 세션, 병렬, 재개)은 플랫폼의 것을 쓰고, 우리가 짓는 것은 넷이다.

| 짓는 것 | 무엇 | 지금 가진 재료 |
|---|---|---|
| **계약** | 일을 시작하기 전에 "무엇이 참이 되고 어떻게 보일 것인가"를 적어 얼린다. 일의 크기만큼만. 이것이 "적당히"다 | 화면 계획, 시나리오, 비례 검사 |
| **눈과 손** | 웹, iOS, Android, Mac, Windows, 게임을 띄워서 보고 누른다. 프로젝트가 이미 가진 테스트와 흐름을 먼저 쓴다 | 걷기, 측정, 필름스트립, QA 브라우저 |
| **검증자** | 만든 쪽이 아닌, 깨끗한 맥락의 에이전트가 계약을 하나씩 증명하거나 반증한다. 계약과 오라클은 만드는 쪽이 못 고친다 | 게이트, 교차 검토 |
| **증거** | 소유자가 30초에 읽는 한 장: 전/후 화면, 필름, 통과한 주장, 확인 못 한 것 | 장부, 감사 화면 |

그 위에 얹는 둘: **취향 묶음**(한국 소비자 앱의 디자인 핸드북, 게임 감각 등. 규칙이 아니라 계약에 들어가는 기준과 검증자의 눈)과 **프로젝트의 기억**(지도, 결정, 진행. 어느 폴더든 이어서 할 수 있게).

## 버리는 것, 남기는 것

- **버린다(새 일의 기본 경로에서):** 프로젝트마다의 컨테이너, 도구를 뺏은 엔진 브리지, 고정된 관문 순서, 시간과 라운드의 고정 한도, 자체 계획 형식에만 묶인 걷기(표식), 집의 디자인을 통과 조건으로 쓰는 것.
- **남긴다(도구로):** 측정(`qa/collector`, `qa/checks`), 걷기 엔진, 필름스트립, 디자인 핸드북과 테마 생성기, 제품 지도와 로드맵의 프롬프트, 비례 범위 계산, ntfy 알림, 문(git 교환).
- **그대로 둔다:** 지금의 데몬과 그 안의 프로젝트들. 돌아가는 것을 부수지 않는다. 새 기능은 거기에 더하지 않는다.
- **나중:** 데스크톱 앱. 증거와 진행은 파일과 HTML로 나오므로 앱은 그것을 보여 주는 뷰어가 된다.

## 모양

프로젝트는 폴더다. 하네스는 Claude Code 플러그인이고(스킬 형식은 Codex, Cursor에서도 읽힌다), 프로젝트 안에 `.sz/`를 둔다.

```
.sz/map.md              프로젝트 지도: 무엇인가, 대상별로 어떻게 띄우고 보고 누르는가, 이미 있는 테스트와 흐름
.sz/contracts/<id>.json 일 하나의 계약: 요청, 레인, 주장들(각각 무엇으로 보이는가), 하지 않는 것, 위험
.sz/evidence/<id>/      검증자가 모은 것: 주장별 판정, 화면, 필름, 로그, report.html
.sz/progress.md         덧붙이기만 하는 진행 기록. 결정과 이유
```

**레인(적당히).** 요청마다 먼저 크기와 위험을 본다. 이것은 모델 호출이 아니라 스킬의 한 단락이다.

| 레인 | 언제 | 절차 | 증거 |
|---|---|---|---|
| S | 파일 몇 개, 새 화면이나 스키마 없음 | 바로 고친다 | 가장 가까운 테스트, 화면이 바뀌면 전/후 한 쌍 |
| M | 기능 하나 | 주장 3~7개의 계약 → 구현 → 검증자 1회 | 주장마다 판정, 흐름 하나의 필름 |
| L | 여러 기능, 새 제품 | 소유자에게 묻기(소유자만 답할 수 있는 것, 5개까지) → 명세와 마일스톤 → 마일스톤마다 계약·구현·검증 | 마일스톤마다 한 장, 끝에 전체 |

한도는 죽이는 스위치가 아니다. 시간과 토큰은 체크포인트에서 보고하고, 멈추는 것은 소유자다.

**눈과 손(`sz-eyes`).** 대상마다 같은 세 가지를 한다: `look`(화면, 화면 위의 글과 컨트롤 목록, 측정), `do`(흐름을 실행하고 필름을 남긴다), `evidence`(한 장으로 묶는다). 형식은 각 대상의 표준을 쓴다: 웹은 Playwright, 모바일은 Maestro YAML, Godot은 GUT, Unity는 PlayMode 테스트. 자체 표식을 제품 코드에 요구하지 않는다. 소유자의 시뮬레이터, 브라우저, 작업 폴더는 건드리지 않는다(전용 시뮬레이터, 헤드리스 브라우저, worktree. 프로젝트의 스크립트가 어디에 쓰는지 먼저 읽는다).

**검증자.** 서브에이전트. 소스는 읽기만 하고, 계약과 `sz-eyes`만 가지고 제품을 조작한다. 기본값이 "아직 증명되지 않음"이다. 만드는 쪽은 얼린 계약과 계약이 가리키는 흐름·테스트를 고칠 수 없다(훅이 막는다). 끝내려 할 때 증명되지 않은 주장이 있으면 Stop 훅이 무엇이 남았는지 말한다.

## 순서

1. **첫 조각 (지금):** `sz-eyes`의 웹(`look`, 측정)과 iOS(전용 시뮬레이터, Maestro, 화면/영상), 계약 형식, 증거 한 장, 스킬 `onboard`와 `work`, 검증자, 훅. credeal(네이티브)과 한판(웹)에서 실제로 돌린다.
2. 긴 일: 플랫폼의 워크플로와 백그라운드 세션으로 L 레인(계획자 → 마일스톤 → 검증자). 진행은 `.sz/progress.md`, 알림은 ntfy.
3. 대상 넓히기: Android, 웹 게임(상태 훅), Godot, macOS 앱, Windows(러너).
4. 취향 묶음: 디자인 핸드북을 계약에 넣는 기준과 검증자의 체크리스트로 옮긴다.
5. 뷰어: 여러 프로젝트의 계약과 증거를 한 화면에서.

## 소유자와 만나는 면

스튜디오는 계획 검토, 문서 메모, 줄 코멘트, 시안 책상을 데스크톱 앱에 직접 지었다. 그 층은 이제 밖에 있다: Plannotator(Apache-2.0, 로컬, 2026-11-15에 저장소에서 확인)는 계획과 HTML과 diff에 메모를 달아 에이전트에게 돌려보내고, 에이전트가 질문과 파일을 남기는 받은편지함을 준다. Claude Code의 Artifact도 같은 일을 한다. 그래서 새 하네스는 검토 화면을 짓지 않는다. 계약은 마크다운으로, 증거는 HTML 한 장으로 내고, 소유자는 가진 도구(Plannotator, Artifact, 브라우저)로 읽고 메모한다. 데스크톱 앱은 그 뒤다.

## 돈 (같은 날의 조사, 출처는 조사 기록에)

- **하네스나 스킬 묶음을 파는 길은 지금 막혀 있다.** 가장 많이 쓰는 것들이 무료이고(Superpowers는 MIT), 결제 API로 확인되는 스킬 키트의 매출은 수백 달러 수준이며, ShipFast는 월 $126K에서 $2K로 떨어졌다. 모델 회사가 기능을 몇 주 안에 흡수한다. Claude 구독을 남에게 되파는 것은 약관이 막는다. 돈을 버는 사람은 청중이 있는 사람이다.
- **공장으로 쓰는 길은 배포가 정한다.** 새 앱의 17%만 2년 안에 월 $1K에 닿는다. 속도만으로는 엣지가 아니다: 배포, 좁은 고객, 검증, 취향의 순서다.
- **한국에서 트래픽이 붙어 있는 곳은 앱인토스다.** 미니앱 1만 개, 파트너의 67%가 혼자, 63%가 수익 발생(금액 무관, 중앙값 미공개, 2천 개일 때 74%에서 내려옴). 사례는 대부분 토스 자신의 글이다. 광고 수수료 15%, 심사 3~5일, 라이트 모드만, 게임은 등급 분류 필요.
- **검증을 내세운 고정가 제작**(500만~1,500만 원)은 가장 빠른 현금이고, 고객 불만(범위가 흐려 재작업, AI가 만든 것의 보안 구멍)과 정확히 맞는다. 일을 멈추면 수입도 멈춘다.

그래서 하네스의 엣지(증명, 취향, 속도)는 팔 물건이 아니라 이 두 길에서 한 사람이 작은 스튜디오처럼 움직이게 하는 도구다. 어느 길로 먼저 갈지는 소유자가 정한다.

## 모르는 것

- 검증자가 실제로 얼마나 잡는가. "Claude는 기본 상태로는 서툰 QA다"가 Anthropic 자신의 말이다. 검증자의 프롬프트는 실제 결함을 심어 놓고 재면서 다듬어야 한다.
- Windows와 Mac 앱의 무인 검증은 권한과 VM 때문에 손이 많이 간다. 3번에서 실제로 재 본다.
- 재미, 게임 감각, 소리는 자동으로 판정할 수 없다. 증거를 소유자에게 보이는 데서 멈춘다.
- 플러그인을 돈 받고 파는 통로는 지금 없다. 수익의 길은 따로 본다(같은 날의 조사).
