# 플랫폼별 디자인 핸드북(모바일 · 웹)과 그것을 재는 디자인 랩

2026-11-13. 소유자의 전제: "버그가 있으면 쓰다 이탈하지만 UI가 구리면 진입조차 하지 않는다."

## 1. 왜

스튜디오가 엔진에게 주는 디자인 지침은 네 군데에 흩어져 있고(`codingSystemPrompt`의 공용 문단, `MOBILE_DESIGN`, `HOUSE_BAR_*`, `web_guidance`), 대부분 "무엇을 하지 말라"와 "첫 화면의 기준"이다. 화면을 **어떻게 짜는지**(구성, 부품, 글자의 자리, 색의 양, 그림을 언제 만드는지)는 거의 없다. 어제 종이 색과 서체를 고쳤고 화면에는 반영됐지만, 리뷰어의 점수는 오르지 않았다.

| 리뷰어 축 (0~10) | 11-13 낮의 시안 | 고친 뒤의 시안 |
|---|---|---|
| 위계 | 5.3 | 5.0 |
| 여백 | 4.3 | 5.3 |
| 타이포 | 6.0 | 5.7 |
| 색 | 7.7 | 6.7 |
| 총점 | 59 D | 51.9 D |

고친 뒤의 시안 세 장과 웹 빌드 한 건을 직접 열어 쟀다(`.design-lab/production/`).

| | 시안 a | 시안 b | 시안 c | 웹 빌드 |
|---|---|---|---|---|
| 첫 화면에서 브랜드 색 픽셀 | 5.8% | 17% (+ 검정 띠 30%) | 6.1% | |
| 12px 이하로 놓인 글자 (글자 수 기준) | 56% | 78% | 48% | |
| 가장 큰 크기로 놓인 것 | 1 | 2 | 2 | |
| 첫 화면의 컨트롤 | 5 | 4 | 21 | |
| 돌아간 글자 / 세로로 쌓인 글자 | 0 / 0 | 0 / 2 | 15 / 0 | |
| 서체 | Pretendard | + Bricolage | + Fraunces | + Gowun Batang 96px, Instrument Serif, Geist Mono |
| **스튜디오의 `check_mockup`이 말한 것** | | **"0 blocker, 0 major, 0 minor. Nothing here holds the page back."** | | 감사 없음 (초안 트랙) |

마지막 줄이 핵심이다. 엔진은 그리는 동안 스튜디오의 측정을 받는데, 그 측정은 위의 어느 것도 보지 못한다. 엔진은 "문제없다"는 답을 받고 멈췄다. 지침에 양이 없고, 양을 재는 것도 없다.

## 2. 목표, 비목표, 반목표

**목표**
1. 모바일 앱과 웹에 각각 **핸드북**을 둔다: 화면 구성, 부품, 글자, 색, 그림에 대해 규칙마다 `기본값 / 이유 / 주제가 뒤집는 조건 / 재는 법`.
2. 엔진, 리뷰어, 측정이 **같은 규칙을 같은 번호로** 말한다.
3. 잴 수 있는 규칙은 `check_mockup`과 감사가 잰다. 엔진이 그리는 동안 받는 답이 달라져야 한다.
4. 서체는 Pretendard · SUIT · SUITE **셋으로 고정**하고, 제품 하나에 하나만 쓴다.
5. 어떤 규칙이 실제로 화면을 바꾸는지 **전후를 재서** 남길 것과 버릴 것을 가른다(디자인 랩).

**비목표**
- 모바일 키트의 부품을 늘리는 일. 랩이 가려낸 규칙을 부품으로 굳히는 것이 순서이고, 키트는 실제 Expo 프로젝트에서 검증해야 한다. 다음 건으로 둔다.
- 네이티브(iOS · Android)에서의 서체 로딩. 네이티브 빌드는 이 스튜디오에서 아직 한 번도 검증된 적이 없다.

**반목표** (동작하더라도 실패인 것)
- 스튜디오의 얼굴. 모든 제품이 같은 화면이 되는 고정 스타일. 값 대신 범위와 조건을 준다(ARCHITECTURE §7.1, §8.6-3과 같은 입장).
- 아무도 재지도 묻지도 않는 규칙. 그런 규칙은 어제의 "브랜드는 한두 군데에만"처럼 지켜지지 않는다.
- 길어서 읽히지 않는 지침. 플랫폼 하나의 핸드북은 프롬프트에서 1,500단어를 넘지 않는다.

## 3. 접근

| | 내용 | 버린 이유 / 고른 이유 |
|---|---|---|
| A | 원칙을 더 쓴다 (프롬프트만) | 오늘의 실패가 이 방식의 결과다. 양 없는 원칙은 지켜지지 않았다 |
| **B** | **기본값과 이탈 조건이 있는 핸드북 + 같은 번호의 측정과 리뷰** | 고름. 규칙이 숫자를 갖되 주제가 뒤집을 수 있고, 뒤집지 않은 이탈은 측정에 걸린다 |
| C | 고정 하우스 스타일 (숫자 고정) | 가장 빨리 일관되지만 모든 제품이 한 얼굴이 된다. 기존 입장과 충돌 |

소유자가 B를 골랐고, 팔레트에 역할을 더하는 코드 변경까지 포함하기로 했다.

## 4. 설계

규칙에는 번호가 있다: `T`(글자), `C`(색), `M`(모바일 구성), `K`(부품 어휘), `P`(웹 페이지), `A`(웹 앱), `I`(그림). 아래 숫자는 기본값이고, 임계값(측정이 결함으로 세는 선)은 랩의 분포를 보고 확정한다.

**기본값을 뒤집는 방식.** 뒤집음을 선언하는 칸(방향표나 페이지 메타의 새 필드)은 만들지 않는다. 규칙은 기본값이고, 엔진은 주제에서 나온 이유가 있을 때만 벗어나며 끝낼 때 그렇게 말한다. 측정의 선은 기본값이 아니라 **분명한 실패**에 긋는다: 예산이 첫 화면의 10%인 규칙의 결함선은 15% 이상이다. 기본값과 결함선 사이가 주제에 주는 여유다. 그 안의 이탈이 옳았는지는 리뷰어와 소유자가 본다. 규칙 쉰 개마다 뒤집는 조건을 적는 일도 하지 않는다: 조건이 분명한 몇 개(C3의 웹 페이지, C8, M9)에만 적었다.

**이전에 만든 프로젝트와 시안.** 씨앗(`theme.json`)이 원본이고 스타일시트는 거기서 만든 것이다. 옛 생성기로 만든 스타일시트는 그 프로젝트의 다음 작업이 시작될 때 같은 씨앗에서 다시 만든다(`display`는 버리고 서체는 Pretendard). 제목 서체가 묻지 않고 바뀌는 것은 "서체는 반드시 고정"이라는 소유자의 결정에 따른 것이다. 옛 시안 페이지가 이름 부르던 서체 파일은 더 넣지 않으므로 그 제목은 Pretendard로 보이고, 다시 재면 `type/second-family`가 적힌다.

### 4.1 서체: 셋으로 고정, 제품에 하나 (T1)

- 씨앗의 `display`(제목 서체 네 짝)를 없애고 `face: 'pretendard' | 'suit' | 'suite'`로 바꾼다. 제목은 같은 서체를 굵게 쓴다. 세리프, 두 번째 고딕, 이탤릭은 없다.
- 고르는 기준(엔진에게 주는 말): Pretendard는 중립적이고 정보가 많은 제품, SUIT는 기하학적이고 또렷한 제품, SUITE는 넓고 부드러운 소비자 제품.
- 모노는 코드 블록(`code`, `pre`, `kbd`) 안에서만. 날짜와 숫자는 본문 서체의 `tabular-nums`.
- **스튜디오가 파일을 준다.** SUITE는 npm에 없어서(GitHub뿐) 엔진에게 설치를 맡기면 실패한다. 세 서체의 woff2를 프로젝트의 `.studio-zero/fonts/`에 넣고, 테마 스타일시트가 `@font-face`로 가리킨다. (Pretendard 2.0MB, SUIT 0.62MB, SUITE 0.54MB. 프로젝트에는 고른 서체 하나만 넣는다.)
- 시안 페이지에는 세 서체를 스튜디오가 넣는다(Pretendard는 조각, SUIT · SUITE는 통째). Geist, Fraunces, Instrument Serif, Bricolage Grotesque는 더 넣지 않는다.
- 새는 곳 일곱 군데를 다 막는다: 씨앗, 계약의 허용 목록, 모노, 시안 서체 주입, 리뷰어 지침("세리프 제목은 결함이 아니다"), 웹 기준 3항("서체 둘"), 엔진의 직접 설치 안내.
- 측정: `type/second-family`(한 화면에 본문 서체가 둘 이상), `type/mono-outside-code`.

### 4.2 글자: 역할과 예산 (T2~T7)

| 역할 | 모바일 | 웹 페이지 | 웹 앱 |
|---|---|---|---|
| 숫자 하나 (figure) | 30~48 / 800, tabular | | 24~36 / 700 |
| 헤드라인 (display) | | 데스크톱 56~96 · 폰 36~44 / 700~800, 자간 −0.02em, 행간 1.05~1.15 | |
| 제목 | 20~24 / 700 | h2 30~40 / 700 | 페이지 제목 24~30 / 700 |
| 소제목 | 18 / 700 | h3 20~24 / 700 | 18 / 600~700 |
| 본문 | 16 / 400~500 | 16, 리드 18~20 | 14~16 |
| 보조 | 14 | 14 | 14 (표 칸) |
| 캡션 | 12 / 500 | 12 | 12~13 / 600 (표 머리) |
| 마이크로 | 11 / 600 | 11 | 11 |

- **T3 작은 글자의 예산.** 12px 이하는 시각, 단위, 뱃지, 스탯 라벨, 표 머리의 것이다. 문장을 놓지 않고, 그 화면의 주된 정보를 싣지 않는다. 한 화면 글자의 약 3분의 1까지. (오늘 48~78%였다. 어제 "작은 단계는 라벨용"이라고만 쓰고 상한을 두지 않은 결과다.)
- T4 굵기는 한 화면에 셋까지(400, 600 또는 700, 숫자 하나에 800).
- T5 글자는 가로로 선다. 돌린 라벨, 한 글자씩 세로로 쌓은 한글, 뒤집힌 눈금 숫자는 없다.
- T6 글은 시작 쪽 정렬. 끝 쪽 정렬은 열을 이룬 숫자만. 가운데 정렬은 숫자 하나와 빈 상태만.
- T7 본문 행간 1.5~1.6, 제목 1.2~1.3, 숫자 1.0~1.1. 라벨은 세 줄로 넘어가지 않는다.
- 측정: `type/micro-overuse`, `type/micro-sentence`, `type/turned-text`, `type/stacked-text`, `type/end-aligned-block`.

### 4.3 색: 역할과 예산 (C1~C8)

- **C1 역할.** 종이(bg) · 표면(surface) · 웰(sunken) · 선(border) / 잉크(fg, fg-muted) / 브랜드(brand, on-brand, brand-soft) / **둘째(second, on-second, second-soft): 신설** / **계열(series-1…6): 신설** / 상태(danger, success, warning).
- **C2 예산.** 채도 있는 색(브랜드, 둘째, 계열, 상태의 면)은 첫 화면의 약 10%. 브랜드 면이 가는 곳: 주 동작, 선택된 것의 표시, 숫자 하나의 판, 진행 막대의 채움. 카드, 패널, 열, 머리 띠, 섹션 배경에는 가지 않는다.
- C3 무거운 면. 모바일과 웹 앱에서 밝은 화면 한가운데의 검정(반전) 띠는 없다. 어두움은 화면 전체의 방식이지 한 구역의 장식이 아니다. 웹 페이지는 반전 섹션을 하나까지.
- **C4 두 편 · 여러 갈래.** 브랜드는 이쪽(나, 우리, 이것), 둘째는 저쪽. 표시로만 쓴다: 숫자의 색, 4px 모서리, 점, 막대의 한 토막. 색만으로 구분하지 않고 이름이나 자리가 같이 간다. 셋 이상은 계열 색을 주어진 순서대로. 색을 지어내지 않는다. (오늘의 결투 화면: 토큰에 색이 하나뿐이라 "두 선수"를 브랜드 대 흰색으로 나타냈고, 한쪽 카드 전체가 파랗게 됐다.)
- C5 옅은 면(brand-soft)은 한 구역까지: 선택된 줄, 오늘의 열.
- C6 상태색은 상태에만.
- C7 컨트롤과 표면에 그라디언트 없음.
- **C8 팔레트를 고르는 법** (`set_theme`의 설명과 지침에): 색상은 주제의 물건에서. 채도는 결에 따라(도구 · 금융 0.12~0.16, 소비자 0.17~0.22, 놀이 · 운동 0.23~0.28). 종이는 차가운 회색이 기본. `second_hue`는 제품에 두 편이나 갈래가 있을 때만 고르고, 아니면 생성기가 낸다. 모서리는 성격에 따라(sharp: 도구 · 데이터, soft: 기본, round: 친근한 소비자 제품).
- 생성기: 둘째는 면으로 칠했을 때 맑은 다섯 색상(주황 50°, 하늘 215°, 파랑 255°, 보라 300°, 자홍 345°) 가운데 브랜드에서 가장 먼 것이고, 그 색상이 힘을 갖는 밝기에 둔다(주황은 밝을 때만 주황이다). 채도는 브랜드보다 한 단계 낮게, 그 위의 글자는 브랜드와 같은 방식으로 AAA를 푼다. 처음에는 브랜드의 보색을 브랜드의 밝기에 뒀는데, 코발트의 상대가 어두운 올리브가 됐다. 계열 여섯은 브랜드 색상에서 시작해 고르게 벌리고 밝기를 번갈아 색각 이상에서도 갈리며, 호박색과 라임 사이(종이 위에서 보이려면 탁해지는 구간)에 떨어진 색상은 옆의 주황이나 초록으로 옮긴다.
- 측정: `color/flood`(첫 화면의 채도 픽셀 비율), `color/dark-band`(밝은 화면의 어두운 픽셀 비율). 픽셀로 잰다: SVG로 그린 면은 DOM의 배경색으로는 보이지 않는다.

### 4.4 모바일: 화면을 짜는 법 (M1~M16)

- **M1 뼈대.** 앱 바(제목 14자 이내, 맥락 한 줄, 동작 둘까지) / 본문(한 열, 좌우 16) / 아래(주 동작 하나의 도크, 또는 최상위 화면의 탭 바 3~5). 둘을 겹쳐 쌓지 않는다.
- **M2 첫 화면은 세 가지를 차례로 답한다.** 지금 어디인가(상태) → 지금 무엇을 하나(동작) → 무엇에 근거하나(첫 증거). 상태 구역은 화면 높이의 3분의 1까지, 동작은 늘 보이고(도크), 나머지는 스크롤한다.
- **M3 숫자 하나.** 숫자 크기로 놓이는 것은 화면에 하나. 두 값을 견줄 때는 한 표면 위의 비교 구역 하나에 같은 크기로 놓고, 차이는 한 번만 말한다.
- **M4 한 번만 말한다.** 날짜, 회차, 격차, 이름과 점수는 화면에 한 번. 앱 바의 제목을 본문에서 되풀이하지 않는다.
- **M5 담는 것.** 기본은 종이 위의 섹션(제목 18/700 + 내용, 사이 24~32). 카드(표면 + 헤어라인, 패딩 16)는 통째로 눌리는 물건, 떠 있는 것, 비교 구역에만. 카드 안의 카드 없음. 같은 높이의 쌍둥이 카드 없음(한 표면에 구분선). 담는 것의 높이는 내용의 높이다.
- **M6 목록.** 같은 종류의 항목은 카드가 아니라 줄: 높이 56~72, 앞(아이콘 · 아바타 40) + 제목 16/600 + 메타 한 줄 14 + 뒤(값 · 꺾쇠), 안쪽으로 들인 헤어라인. 첫 화면에 5~8줄.
- M7 밀도. 첫 화면의 컨트롤은 줄과 앱 바를 빼고 7개까지. 한 구역에 메타 줄은 둘까지.
- M8 스탯. 라벨(12/500) + 값(20~30/700, tabular) + 단위(값의 60%). 한 줄에 셋까지.

### 4.6 웹: 두 종류를 가른다

**P1.** 경로마다 먼저 정한다: 읽히고 설득하는 **페이지**인가, 일하는 **앱 화면**인가. 도구에 마케팅 히어로를 얹지 않고, 랜딩을 대시보드로 만들지 않는다.

**페이지 (P2~P10)**
- P2 격자와 폭. 내용 폭 1120~1200, 12열 · 간격 24. 글 열은 68ch(한글 38~42자). 섹션 사이 데스크톱 96~128 · 폰 56~72.

## 5. 검증: 디자인 랩

**물음.** 핸드북과 새 측정을 받은 엔진이 그린 화면이, 받지 않은 엔진의 화면보다 나은가. 낫다면 어느 규칙 때문인가.

**방법.** "전"과 "후"는 소스 트리 둘이다: `962af1f`에 얼린 작업 트리(`.design-lab/src-baseline`)와 이 브랜치. 각 트리가 하네스와 똑같이 프롬프트를 만들고(`codingSystemPrompt` + `directionBrief` + 그 트리의 테마), 각 트리의 `MockupRenderer.check`가 `check_mockup` 노릇을 한다(로컬 Chrome, 루프백 주소). 같은 브리프, 같은 방향표, 같은 모델(Opus, 추론 강도 high: 오늘 스튜디오의 엔진과 같다)로 방향마다 에이전트 하나가 그린다. 달라지는 것은 지침, 테마, 측정뿐이다.

| | 브리프 | 템플릿 | 방향 |
|---|---|---|---|
| duel | 오늘의 실제 프로젝트(다이어트 결투)의 PRD, 화면 명세, 방향표 | mobile-expo | a, b, c |
| dues | 러닝 모임 회비 정산 (목록 · 입력이 많은 앱) | mobile-expo | a, b |
| quote | 견적서 서비스의 소개 페이지 (웹 페이지) | web-vite-react | a, b |
| orders | 1인 쇼핑몰 주문 관리 (웹 앱: 표) | web-vite-react | a, b |

새 브리프 셋은 스튜디오의 주 엔진 노릇을 하는 에이전트가 기준선의 지침으로 쓴다. 방향 9개 × 두 군 = 18장, 여기에 오늘 실제 엔진이 그린 3장.

**재는 것.**
1. 규칙마다 그 규칙의 숫자(`scripts/design-lab/metrics.mjs`): 브랜드 · 채도 · 어두운 픽셀, 작은 글자 비율, 서체 수, 가장 큰 크기의 개수, 컨트롤 수, 반쯤 빈 카드, 돌아간 · 쌓인 글자, 끝 정렬된 글, 두 번 말한 숫자.
2. 스튜디오의 측정이 한 말(검사 결과의 수와 종류).
3. 눈가림 리뷰: 리뷰어 지침(`VISION_SYSTEM_PROMPT`, 기준선 것으로 양쪽 다)을 받은 에이전트 셋이 어느 군인지 모른 채, 섞인 순서로, 일곱 축을 매긴다. 실제 리뷰어(Codex)와 벤더가 다르다는 한계가 있다.
4. 규칙별 판독: 같은 리뷰어들이 핸드북을 점검표로 받아(양쪽 군의 화면 모두에 대해) 화면마다 어긴 규칙의 번호를 적는다. 숫자가 없는 규칙(P, A, K와 M의 대부분)은 이것으로 전후를 본다: 규칙마다 "어긴 화면 수"가 기준선과 처리군에서 얼마인가. 웹 페이지의 P3 · P4에는 숫자도 붙인다(헤드라인의 줄 수, 첫 화면 좌우 절반의 빈 비율).
5. 궤적: 검사 서버가 호출마다 그때의 페이지와 답을 남긴다. 처리군의 첫 초안(지침만의 효과)과 마지막(측정을 받고 고친 뒤)을 가를 수 있다.

**판정.** 규칙은 셋 중 하나가 된다. ① 그 규칙의 숫자가 움직였고 리뷰 점수가 떨어지지 않았다: 남긴다. ② 숫자가 움직이지 않았다: 문장을 고치거나 측정을 붙여 한 번 더 본다. ③ 숫자는 움직였는데 화면이 나빠졌다: 버린다. 결과는 한 페이지로 소유자에게 보인다(전후 화면을 나란히, 숫자와 함께). **소유자가 그 페이지를 보고 남길 것을 정하기 전에는 `main`에 합치지 않고 배포하지 않는다.**

**한계.** 방향 하나에 한 장씩이라 표본이 작다. 한 장의 차이는 읽지 않고, 열여덟 장에 걸친 규칙별 분포를 읽는다. 애매한 규칙은 표본을 더 뽑는다. 그림 규칙과 빌드(React Native 코드)는 이 랩으로 볼 수 없다.

## 8. 둘째 회차: 화면의 재료 (같은 날 저녁)

### 8.1 무엇이 틀렸나

비교 페이지를 본 소유자의 말: "전/후가 모두 별로", "화면 자체가 밋밋함", "전후 고르는게 의미가 있나 싶은 수준". 살아 있다고 꼽은 제품은 닌텐도, 네이버쇼핑, 치지직, 당근, 토스였다.

그 다섯 곳(토스는 앱 화면이 웹에 없어 넷과 닌텐도 스토어)의 모바일 첫 화면과 우리 화면을 같은 자로 쟀다. 감사의 폰 크기(393×659)에서 수집기가 읽은 값:

| | 그린 것이 덮은 면 | 아이콘 | 헤어라인 그은 상자 |
|---|---|---|---|
| 레퍼런스 5곳 | 9~60% | 11~27 (한 곳 1) | 0 (한 곳 1) |
| 옛 지침과 첫 핸드북의 화면 14장 | 0%, 또는 차트 하나 | 0~4 | 1~8, 11장이 3 이상 |

첫 핸드북(§4.3~4.7)은 빼는 규칙뿐이었다: 강한 색은 10분의 1, 아이콘은 잉크색, 사람은 이니셜, 카드는 헤어라인, 장식 그림 금지. 결함은 없앴고 재료는 그대로였다. 눈가림 리뷰의 절대 점수가 움직이지 않은 까닭이고, 소유자가 한눈에 본 것이다. 어제의 기준 사이트 여덟 곳이 개발 도구와 포트폴리오 같은 미니멀 웹이었던 것도 같은 쪽으로 기울게 했다.

### 8.2 무엇을 바꿨나

"쓸데없는 그림을 넣지 않는다"는 원칙은 남긴다. 바뀐 것은 선이다. 어느 제품에나 놓일 수 있는 장면은 여전히 금지이고, **이 제품의 명사를 그린 것**(사람의 아바타, 제품이 이름 부르는 물건, 상태를 보이는 히어로 그림, 줄마다의 아이콘)은 재료다.

| 규칙 | 전 | 후 |
|---|---|---|
| C2 | 강한 색은 첫 화면의 10분의 1, 카드와 띠에는 금지 | 상태를 담는 히어로 하나에 강한 색, 3분의 1까지. 둘째로 채운 카드는 없다. 45%를 넘으면 넘침 |
| C4 | 편은 표식으로만 | 둘을 견주는 블록 하나에서는 각 편이 제 절반을 채울 수 있다 |
| C5 | 옅은 색은 한 구역 | 아이콘 타일, 배지, 고른 줄, 오늘 칸 |
| E1~E5 (새로) | | 첫 화면은 글자와 선만으로 만들지 않는다 / 사람은 아바타, 물건은 그린 것, SVG 한 가지 화풍 / 아이콘 타일과 배지 / 캔버스는 bg-sunken, 카드는 테두리 없이 / 문장은 맨 나중 |
| M1 | 도크 아니면 탭 바 | 최상위 화면은 탭 바와 그 위에 떠 있는 알약 하나, 깊은 화면은 도크. 떠 있는 것 아래에 놓이는 것은 없다 |
| M5, M6 | 종이 위의 구획, 헤어라인 카드와 줄 | 카드 위의 줄, 아바타나 아이콘 타일이 앞에 |
| M7 | 누를 것 일곱 | 탭은 세지 않는다. 블록의 종류를 섞는다 |
| M12 | 빈 상태에 그림 금지 | 있을 것을 그린 작은 그림 하나 |
| I1~I3, I7 | 그 밖에는 그림 없음, 사람은 이니셜, 아이콘은 잉크색 | 사람과 물건과 아이콘은 코드로 그린다. 금지는 스톡 장면, 3D 덩어리, 추상 그라디언트, 이모지 |

핸드북은 플랫폼 하나에 1,500단어에서 1,900단어 가까이가 됐다.

폰의 규칙에는 하한을 넣었다(C2, E1, E3은 폰과 웹의 문장이 다르다). 처음에는 "3분의 1까지", "종류를 이름 붙이는 줄에는"처럼 상한과 조건으로 적었고, 랩의 엔진은 색을 그대로 두고 아이콘을 검사가 묻는 수에서 멈췄다. 지금은: 첫 화면에 브랜드 색 히어로가 하나 있고 화면의 5분의 1에서 3분의 1, 그린 것이 5분의 1 이상, 아이콘과 아바타가 열두 개 이상, 줄과 탭과 칩과 수치마다 아이콘. 웹에는 넣지 않았다. 자를 댄 곳이 폰이다.

측정:

- `color/flood`의 한도 0.15 → 0.45. 옛 한도는 소유자가 좋다고 한 화면 전부를 넘침으로 불렀다.
- `material/nothing-drawn` (E1, 메이저): 첫 화면에 그린 것이 8% 미만이고 아이콘이 10개 미만. 다섯 레퍼런스 가운데 가장 덜 그린 곳(8.6%, 11개) 바로 아래다.
- `material/ruled-boxes` (E4, 메이저): 헤어라인 그은 상자가 3개 이상.
- 둘 다 제품의 첫 화면에서, 폰 크기에서만 묻는다. 자를 댄 곳이 거기다.
- `layout/too-many-controls`는 탭을 세지 않고 마이너로 내렸다. 레퍼런스의 첫 화면은 누를 것이 8~28개다.
- 리뷰어의 클립아트 함정에 "이 제품의 명사를 제품의 화풍으로 그린 것은 클립아트가 아니다"를 더했다. 색 축의 물음에서 "아껴 쓰는가"를 뺐다.

### 8.3 걸려 있는 것

- **절반쯤 왔다.** 하한을 넣은 핸드북으로 그린 폰 화면 다섯 장의 강한 색은 가운데 값 17%(레퍼런스 25%, 덧붙임 실험 26%), 아이콘 14개(레퍼런스 14, 덧붙임 22)다. 셋은 덧붙임만큼 나왔고, 하나는 중간이고, 하나는 색을 쓰지 않았는데 감사가 통과시켰다. 색의 몫을 재는 검사가 없다. 값과 화면은 `docs/runs/2026-11-13-design-lab/`의 둘째 회차에 있다.

- **소유자가 처음에 지적한 파란 카드.** 그 화면의 파란 면은 첫 화면의 6분의 1이었고, 새 한도에서는 색으로 잡히지 않는다(검정 띠, 작은 글자, 둘째 서체, 그린 것 없음, 헤어라인으로는 잡힌다). 내 읽기로는 그 카드의 문제가 색의 양이 아니라 빽빽한 작은 글자를 담은 무거운 면이었다. 소유자의 눈으로 확인할 것.
- 그림은 엔진이 SVG로 그린다. 레퍼런스의 사진과 입체 아이콘에는 못 미친다. 이미지 생성기는 I1의 자리(음식, 장소, 물건, 얼굴, 게임의 세계)에만 쓰고 여기서는 넓히지 않았다.
- 빌드에서는 재지 않았다. Expo에서 SVG를 그리려면 `react-native-svg`가 필요하고 키트에는 Hero, IconTile, Avatar, TabBar가 아직 없다.
- 웹의 책상 크기 화면에는 재료 검사가 없다. 표가 주인인 화면에 자를 대 보지 않았다.
