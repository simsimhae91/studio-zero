# 열린 저장소: git 문, 들여오기, 에이전트 안내문 (2단계)

2026-11-15. 소유자의 말: "브라운필드 이미 다른것으로 작업하던것을 스튜디오에서 이어 작업하는것도 필요함." 같은 날 두 결정에 답했다("1. 찬성 2. 승인"): 프로젝트의 저장소가 샌드박스 밖으로 나가도 되는가(이 Mac의 git clone으로, git으로만 주고받는다), 그리고 방향과 네 단계의 순서. 1단계(고운 기어)는 그날 끝났다. 이 문서는 2단계이고, 들여올 첫 저장소는 소유자가 가리킨 `~/orca/projects/credeal`이다.

## 지금 (코드와 그 저장소에서 확인한 것)

- 프로젝트의 저장소는 컨테이너 볼륨 안에만 있다. 소유자의 도구(Orca, 터미널의 git)는 닿지 못한다. 밖으로 나가는 길은 Core 프로젝트의 것 하나(`SelfHosting`: 번들로 넣고, 번들로 내고, 빨리 감기만)이고 한 저장소에 묶여 있다.
- 프로젝트는 빈 저장소에서 태어난다(`initWorkspaceScript`). 스튜디오는 제품이 저장소의 루트에 있고, 자기 테마와 키트와 Supabase 위에 지어졌다고 가정한다: 시스템 프롬프트, 초안 지시문, 슬롭 린트, 디자인 게이트가 전부 그 가정 위에 있다.
- credeal: 원격 없음, main에 236커밋, 추적 파일 672개. 루트는 기획안(문서, 덱, HTML 목업)이고 제품은 `app/`의 Expo 58 앱이다. expo-router(`src/app/`), npm 잠금 파일, 자체 테마(Pretendard), 모의 API와 AsyncStorage(계정도 백엔드도 없음), 네이티브 모듈(공유 확장, 클립보드), maestro 흐름 44개. `react-native-web`이 없어서 웹 타깃은 지금 돌지 않는다. 루트에 `AGENTS.md`가 없고 `app/AGENTS.md`(Expo가 준 것)가 있다.

## 2단계가 만드는 것

1. **문**: 프로젝트마다 이 Mac에 git 저장소 하나(`~/.studio-zero/repos/<slug>.git`). 스튜디오의 브랜치가 거기 비치고, 소유자는 거기서 clone하고 거기로 push한다. push는 그 자리에서 스튜디오가 받아들이거나, 이유를 말하고 거절한다.
2. **들여오기**: 이 Mac의 기존 체크아웃이 같은 문으로 스튜디오 프로젝트가 된다. 제품이 저장소의 하위 폴더에 있어도 된다.
3. **맞추기**: 들여온 제품을 스튜디오가 걷고 잴 수 있게 만드는 작업 하나(엔진이 한다): 웹에서 돌게, 화면 계획, 표식. 제품의 모양과 동작은 바꾸지 않는다.
4. **에이전트 안내문**: 저장소 루트의 `AGENTS.md`에 스튜디오가 쓰는 한 구획. 밖의 세션(Orca의 Claude, Codex)이 스튜디오의 약속을 지키게 한다.

만들지 않는 것: 스튜디오 안의 이어지는 대화(3단계), 로드맵을 세션 위로(4단계). GitHub 주소로 바로 들여오기는 하지 않는다: 소유자가 먼저 clone하면 한 줄이고, 데몬이 소유자의 git 자격으로 밖에 나가는 길을 새로 열지 않는다. 문에서 GitHub으로 올리는 것도 소유자의 clone에서 평소대로 한다.

## 문

문은 bare 저장소다. 불변식 하나: **문의 `refs/heads/*`는 프로젝트 컨테이너 저장소의 `refs/heads/*`와 같다.** 진실은 컨테이너에 있고, 문은 그 거울이며, 소유자의 push는 컨테이너가 받아들인 것만 문에 남는다. 체크포인트(`refs/sz/*`)는 비치지 않는다. Core 프로젝트에는 문이 없다(자기 길이 있다).

- **열기** (`repo.open`, `sz clone <slug> [dir]`, 데스크톱의 "저장소"): 문이 없으면 만들고(훅 포함) 비춘다. 처음 여는 것은 소유자의 행동이다. 그전에는 디스크에 아무것도 없다.
- **비추기** (스튜디오 → 문): 컨테이너의 브랜치 가운데 문에 없는 커밋을 번들로 묶어 문에 넣고(`fetch.fsckObjects=true`, 샌드박스에서 나온 객체다), 없어진 브랜치를 지운다. 작업이 끝나거나 멈출 때, 빠른 수정이 들어갔을 때, 합쳤을 때, 체크포인트로 되돌렸을 때 한다. 문이 열린 프로젝트에만. fetch는 훅을 부르지 않는다.
- **받기** (소유자 → 스튜디오): 문의 `pre-receive` 훅이 `sz`를 불러 데몬에 묻는다. 새 객체는 훅이 팩으로 묶어 문 안의 임시 폴더에 두고, 데몬이 그것을 컨테이너에 넣은 뒤 ref를 옮긴다. 데몬이 받아들이면 훅이 0으로 끝나고 git이 문의 ref를 옮긴다. 그래서 "push가 됐다"와 "스튜디오가 갖고 있다"가 같은 말이다. 데몬이 꺼져 있으면 거절한다.

받는 규칙. 전부 확인한 뒤에 전부 옮긴다.

| 무엇 | 규칙 |
|---|---|
| `main` | 앞으로만. 스튜디오의 main이 push의 조상이어야 한다. 아니면 "fetch하고 그 위에 올려서 다시". 지울 수 없다. |
| 다른 브랜치 | 만들기, 옮기기(강제 포함), 지우기 모두 된다. 끝나지 않은 작업이 잡고 있는 브랜치와 본체가 지금 서 있는 브랜치는 안 된다. |
| 태그와 그 밖의 ref | 받지 않는다. |
| 문이 뒤처져 있을 때 | 비추고 거절한다("스튜디오가 그사이 움직였습니다. fetch 후 다시"). |

main을 옮기는 것은 프로젝트마다 한 번에 하나다: 받기는 빠른 수정의 들어가기, 합치기와 같은 잠금을 잡는다(`Slots.landing`). 본체가 main에 서 있으면 작업 파일도 따라오고(커밋 안 된 변경과 겹치면 거절), 큰 작업이 다른 브랜치를 잡고 있으면 ref만 옮긴다.

main을 받은 뒤:
- 잠금 파일이 바뀌었으면 의존성을 다시 놓는다.
- `supabase/`가 바뀌었고 프로젝트에 백엔드가 있으면 마이그레이션을 넣고 결과를 push 출력에 적는다. 실패해도 push는 받은 것이다(코드는 소유자의 것이고, 고치는 길은 앞으로 가는 것뿐이다). 크게 말한다.
- 프리뷰의 개발 서버를 새 코드로 맞춘다.
- 화면 계획이 있으면 **전체 점검**을 건다(이미 줄 서 있으면 그것으로). 소유자의 코드는 검사를 지나 들어온 것이 아니므로, 화면 기준과 걸은 길을 새로 적어야 그 뒤의 빠른 수정이 "원래 있던 것"과 "이번에 생긴 것"을 가를 수 있다. 토큰은 들지 않는다. `repos.checkOnPush: false`로 끈다.

소유자의 push는 검사로 막지 않는다. 엔진의 일은 믿지 않으므로 검사를 지나야 main에 들어가지만, 소유자는 소유자다.

## 들여오기

`sz adopt <경로> [--dir <하위 폴더>] [--base <브랜치>] [--name <이름>]`. 엔진을 쓰지 않고 토큰이 들지 않는다. 책상에서만(이 Mac의 경로를 읽는다).

1. 경로가 git 체크아웃의 루트인지, 기준 브랜치(`--base`, 없으면 `main`, 그것도 없으면 지금 서 있는 브랜치)가 있는지 본다. 커밋되지 않은 변경은 가지 않고, 몇 개인지 말한다.
2. 제품이 어디 있고 무엇인지 커밋에서 읽는다(`git show`): `package.json`에 `expo`가 있으면 `mobile-expo`, `next`면 `web-next`, `vite`와 `react`면 `web-vite-react`. 루트가 아니면 한 단계 아래 폴더들을 본다. 하나면 그것, 여럿이면 `--dir`로 고르라고 말하고, 없으면 거절한다: 스튜디오가 걷고 잴 줄 아는 것은 이 셋이다.
3. 프로젝트를 만든다. `Project.root`(제품 폴더, 루트면 빈 문자열)와 `Project.adopted`(어디서 왔나: 경로, 기준 브랜치)가 붙는다.
4. 문을 만들고 체크아웃의 기준 브랜치를 문의 `main`으로 가져온다(호스트의 git끼리). 문의 main을 번들로 컨테이너에 넣는다. 스튜디오의 통합 브랜치는 언제나 `main`이다. 기준 브랜치의 이름이 다르면 그렇게 말한다(`git push studio develop:main`). 다른 브랜치는 가져오지 않는다: 필요한 것은 소유자가 `git push studio <브랜치>`로 보낸다.
5. 제품 폴더에서 의존성을 설치한다(잠금 파일이 말하는 그대로).
6. 체크아웃에 원격 `studio`를 단다(문의 경로). 같은 이름의 원격이 이미 있으면 건드리지 않고 말한다. 작업 트리의 파일은 하나도 쓰지 않는다.

이 시점에 스튜디오의 main은 소유자의 main과 한 커밋도 다르지 않다. 스튜디오가 저장소에 더하는 것은 전부 맞추기 작업의 브랜치로 오고, 소유자가 합친다.

**제품 폴더.** 들여온 프로젝트에서 샌드박스의 작업 폴더는 `/workspace/<root>`다. 명령의 기본 위치, 파일 도구의 기준, 개발 서버, 타입체크, 화면 계획(`docs/screens.json`)과 `.studio-zero/`가 전부 거기 기준이다. 저장소 전체를 다루는 git 스크립트만 `/workspace`에서 돈다. 이 구분은 샌드박스 층 한 곳에 있다(`OrbStackManager`가 자리 번호를 읽듯 `root`를 읽는다). 바뀐 파일 목록은 저장소 기준으로 읽어 제품 폴더 기준으로 옮기고, 제품 밖의 코드가 바뀌었으면 범위는 전체다(어디에 닿는지 가져오기로 읽을 수 없다).

**들여온 프로젝트에 적용하지 않는 것.** 집의 디자인(테마, 서체 셋, 키트, 슬롭 린트, 디자인 리뷰어의 점수)은 스튜디오가 지은 제품의 약속이다. 들여온 제품은 자기 디자인을 갖고 왔다. 그래서:

- 프로비저닝은 테마, AX 키트, 모바일 키트, 프로젝트 파일을 쓰지 않는다. 의존성만 잠금 파일에 맞춘다.
- 검사 목록에 슬롭 린트를 넣지 않는다. 브라우저 검사의 스위치(시각 검사)는 넣는다.
- 큰 작업은 빠른 트랙으로 돈다: 컴파일, 화면 계획, 스모크, 시나리오 걷기, 명령 검사. 디자인 게이트와 다른 회사 모델의 교차 검토는 돌지 않는다. 디자인 작업(`ideate`)과 로드맵은 거절한다: 둘 다 집의 약속으로 처음부터 짓는 길이다(4단계에서 다시 본다).
- 시스템 프롬프트가 다르다(`ADOPTED_SYSTEM_PROMPT`): 이 제품의 규칙은 이 저장소의 것이고(AGENTS.md, README, 기존 코드), 스택과 구조와 디자인을 바꾸지 않으며, 스튜디오가 재는 것(대비, 터치 영역, 잘림, 가로 스크롤, 한 줄 라벨)과 걷는 법(표식)만 스튜디오의 것이다.

남는 것은 재서 말할 수 있는 것이다: 빠른 수정은 1단계 그대로 돈다(바뀐 화면만, 화면 기준에 없던 결함만 막는다). 전체 점검도 그대로다.

## 맞추기

들여온 직후의 프로젝트는 엔진이 일할 수 있고 컴파일 게이트가 돌지만, 프리뷰와 걷기는 아직 없다. `sz fit <slug>`(데스크톱: "스튜디오에 맞추기")가 작업 하나를 낸다(종류 `adopt`, 소유자의 구독). 지시문(`ADOPT_BRIEF`)이 시키는 것:

1. 저장소를 읽는다. 무엇을 하는 제품이고 화면이 무엇인지.
2. 웹 타깃이 샌드박스에서 돌게 한다(`.studio-zero/project.json`의 명령과 포트). Expo면 웹 의존성을 `expo install`로 넣고, 웹에 없는 네이티브 모듈은 웹에서만 서는 대역으로 가린다. 네이티브 동작은 바꾸지 않는다.
3. 있는 그대로의 화면 계획을 쓴다(`docs/screens.json`, 짧은 형식): 지금 있는 화면, 사람이 하는 일, 시나리오. 계정이 없는 제품은 `noAccounts`.
4. 화면과 단계에 표식을 단다(`data-screen`, `data-step`, `data-done`; React Native는 `dataSet`). 표식은 웹에서만 보이는 속성이다.
5. 모양, 문구, 동작은 바꾸지 않는다. 걷다가 제품의 결함을 만나면 고치지 말고 그 시나리오를 계획에서 빼고 말한다.

검사: 컴파일, 계획이 형식에 맞는지, 스모크, 시나리오 전체 걷기와 화면 측정. 측정에서 나온 결함은 막지 않는다. 들여온 그대로의 것이므로 **화면 기준으로 적는다**: 이 작업이 프로젝트의 첫 걸은 길과 첫 화면 기준을 만든다. 끝나면 하네스가 에이전트 안내문을 쓰고 같이 커밋한다. 브랜치는 문에 비치고, 소유자가 자기 IDE에서 보고 합친다(큰 작업은 스스로 들어가지 않는다).

## 에이전트 안내문

저장소 루트 `AGENTS.md`의 한 구획(`<!-- studio-zero:begin -->`과 `end` 사이). 스튜디오가 프로젝트의 사실로 써 넣고, 구획 밖은 건드리지 않는다. 루트에 `CLAUDE.md`가 없으면 `@AGENTS.md` 한 줄로 만든다(있고 AGENTS.md를 말하지 않으면 같은 구획을 덧붙인다). 내용:

- 이 저장소는 Studio Zero도 일하는 곳이고, 주고받는 길은 원격 `studio`다: 받는 법, 보내는 법, main은 앞으로만.
- 제품이 어느 폴더에 있는지.
- 화면 계획이 어디 있고, 화면을 더하거나 바꾸면 같은 커밋에서 계획과 표식을 맞춘다는 것. `docs/screens.md`는 스튜디오가 쓰는 것이라 고치지 않는다는 것.
- 스튜디오가 화면마다 재는 것, 그리고 `sz check`와 `sz edit`.
- 집의 프로젝트에만: 백엔드의 약속(마이그레이션은 고치지 않고 새로 더한다), 테마 파일은 생성물이라는 것.

들여온 프로젝트는 맞추기 작업이 쓴다. 스튜디오가 지은 프로젝트는 프로비저닝이 다른 스튜디오 파일과 같이 쓴다(없을 때만, 서 있는 브랜치에).

## 신뢰

- 문의 훅은 소유자가 push할 때 소유자의 권한으로 `sz`를 부른다. 훅 파일은 데몬이 쓰고 `~/.studio-zero` 안에 있다. 컨테이너에는 호스트가 걸려 있지 않아 엔진이 닿지 못한다.
- 샌드박스에서 나온 객체는 문에 들어갈 때 fsck한다. git 객체로는 훅도 설정도 오지 않는다. 다만 소유자가 그 브랜치를 자기 IDE에서 체크아웃하면 엔진이 쓴 코드가 소유자의 Mac에 파일로 놓인다. 이것이 결정 1이 연 것이다. 읽고 합치는 것은 지금처럼 소유자다(차이 보기, 줄 코멘트).
- `projects.adopt`와 `repo.receive`는 책상의 소유자만. 들여오기가 소유자의 체크아웃에 쓰는 것은 git 설정의 원격 한 줄이다.

## 확인하는 법

- 문: 진짜 git으로. 테스트 데몬의 문에 `git clone`, `git push`를 하고 받는 규칙의 줄마다 한 번씩.
- 들여오기: 하위 폴더에 제품이 있는 임시 저장소를 들여와 제품 폴더에서 명령이 도는지, 저장소 전체가 커밋되는지.
- 실제: credeal을 들여오고(L0), 맞추기 작업을 소유자의 구독으로 한 번 돌리고, 그 브랜치를 문으로 받아 본다. 한판(`diet-battle-lab`)의 문을 열어 clone하고, 손으로 고친 커밋을 push해 전체 점검이 걸리는지 본다.

## 알고 가는 한계

- 들여온 프로젝트의 큰 작업은 화면 측정으로 막히지 않는다(빠른 수정만 막힌다). 합친 뒤 전체 점검이 새 결함을 보여 준다.
- 걷기와 측정은 웹 타깃이다. 네이티브에만 있는 화면과 동작(공유 확장, 알림)은 보지 못한다. 시뮬레이터 레인은 따로 정할 일이다.
- 문으로 한 번에 받는 팩은 메모리로 지나간다(수백 MB까지).
- 기준 브랜치가 `main`이 아닌 저장소는 push할 때 이름을 바꿔 적어야 한다.
