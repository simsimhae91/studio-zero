출하할 때: 제품의 로그인 앱을 따로 만들기

한 줄 요약

프로토타입은 스튜디오의 공용 앱으로 로그인합니다. 제품을 내보낼 때는 그 제품 이름의 앱을 카카오와 Google에 새로 만들어 호스팅된 Supabase 프로젝트에 연결합니다. 코드는 그대로이고, 바뀌는 것은 설정입니다.

이 글이 확인한 범위. 공용 앱 등록은 실제로 밟아 본 절차입니다. 이 글은 다릅니다. 공식 문서를 따라 정리한 것이고, 제품 하나를 끝까지 내보내며 밟아 본 것은 아닙니다. 확인하지 못한 곳은 그렇다고 적었습니다. 밟아 보는 대로 고칩니다.

왜 따로 만드나

  • 동의 화면에 뜨는 이름과 아이콘이 제품의 것이어야 합니다. 공용 앱으로 내보내면 사용자는 "Studio Zero에 로그인"하게 됩니다.
  • 공용 앱에는 이 Mac의 주소만 등록돼 있습니다. 제공자는 등록된 주소와 완전히 같은 곳으로만 사람을 돌려보냅니다. 제품의 백엔드 주소는 제품의 앱에 등록합니다.
  • 검수와 정책의 단위가 앱입니다. 한 제품의 문제로 다른 프로토타입의 로그인이 막히면 안 됩니다.

프로토타입에서 만든 계정과 데이터는 이 Mac의 로컬 백엔드에 있습니다. 호스팅된 프로젝트는 빈 채로 시작합니다.

1. 호스팅된 Supabase 프로젝트

  1. supabase.com에서 프로젝트를 만듭니다.
  2. 제품의 작업 폴더에서 스키마를 올립니다. 스튜디오가 로컬에 적용해 온 바로 그 마이그레이션입니다. 
    supabase link --project-ref <프로젝트 ref>
supabase db push
  3. 대시보드의 Authentication > Sign In / Providers에서 Kakao와 Google을 열면 콜백 주소가 나옵니다. 이것을 두 콘솔에 등록합니다. 
    https://<프로젝트 ref>.supabase.co/auth/v1/callback

2. 카카오: 제품의 앱

순서는 공용 앱과 같고, 다른 것은 셋입니다.

  • 앱 이름과 아이콘은 제품의 것으로 넣습니다. 동의 화면에 그대로 뜹니다.
  • 비즈 앱. 이메일을 받으려면 필요합니다. 사업자가 있으면 [앱] > [일반] > [비즈니스 정보] > [사업자 정보 등록], 없으면 [개인 개발자 비즈 앱]. 개인 개발자 비즈 앱은 비즈니스 채널을 연결할 수 없습니다.
  • 리다이렉트 URI([앱] > [플랫폼 키] > [REST API 키])에는 위의 Supabase 콜백 주소를 넣습니다.

그다음 Supabase 대시보드의 Kakao 화면에 REST API 키(client id)와 클라이언트 시크릿 코드를 넣고 켭니다.

검수에 대해: 카카오싱크, 친구 목록, 메시지 같은 추가 기능은 검수 대상이고 영업일로 3일에서 5일이 걸린다고 문서에 있습니다. 닉네임, 프로필 사진, 이메일만 받는 로그인에 따로 검수가 필요한지는 공식 문서에서 확인하지 못했습니다. 출시 일정을 잡기 전에 콘솔에서 동의항목의 상태를 직접 확인하십시오.

3. Google: 제품의 클라이언트

  1. 제품용 Google Cloud 프로젝트를 만들고 Google Auth Platform을 시작합니다.
  2. Branding. 앱 이름, 로고, 지원 이메일, 홈페이지, 개인정보처리방침 링크를 넣습니다. 여기와 클라이언트에 쓰는 도메인은 모두 승인된 도메인(Authorized domains)에 먼저 등록돼 있어야 합니다.
  3. Clients. Web application 클라이언트를 만들고 Authorized redirect URIs에 Supabase 콜백 주소를 넣습니다. 시크릿은 만들 때 한 번만 보입니다.
  4. Audience. 게시 상태를 Testing에서 In production으로 바꿉니다. 그래야 아무 Google 계정이나 로그인할 수 있습니다.
  5. Supabase 대시보드의 Google 화면에 Client ID와 Client secret을 넣고 켭니다.

준비해 둘 것이 있습니다. 소유한 도메인의 공개 홈페이지(Search Console에서 소유를 확인한 것)와 개인정보처리방침입니다. 브랜드가 인증되기 전에는 동의 화면에 앱 이름과 로고 대신 도메인만 나옵니다. openid, email, profile만 쓰면 민감한 범위에 요구되는 앱 검증은 받지 않아도 됩니다.

4. 로그인한 사람이 돌아올 주소

대시보드의 Authentication > URL Configuration에서:

  • Site URL: 제품의 주소. 제품이 돌아올 주소를 말하지 않았을 때 사람이 떨어지는 곳입니다.
  • Redirect URLs: 제품이 돌아올 주소로 말할 수 있는 곳들. https://example.com/**처럼 씁니다(**는 무엇이든, *는 .과 /를 넘지 않는 글자들).

제품의 코드는 지금 떠 있는 주소(window.location.origin)를 돌아올 주소로 보냅니다. 그 주소가 Redirect URLs에 없으면 사람은 Site URL에 떨어집니다. 로컬 백엔드에서 본 동작이 그랬습니다. 미리보기 배포 주소에서도 로그인하려면 그 주소의 패턴도 넣습니다.

5. 제품의 환경변수

제품을 배포하는 곳에 세 값을 넣습니다. 이름의 앞머리는 프레임워크를 따릅니다(Vite는 VITE_, Next는 NEXT_PUBLIC_, Expo는 EXPO_PUBLIC_).

이름값
…SUPABASE_URLhttps://<프로젝트 ref>.supabase.co
…SUPABASE_PUBLISHABLE_KEY대시보드의 publishable 키. 브라우저에 실려도 되는 키입니다.
…SUPABASE_LOGINS켠 제공자. kakao,google. 비우면 제품은 이메일 로그인만 보입니다.

secret 키와 service_role 키는 어디에도 넣지 않습니다. 제품의 코드는 그것 없이 돌도록 지어져 있습니다.

6. 기기에서 도는 앱(Expo)

스튜디오가 확인한 것은 웹에서의 로그인입니다. 기기에 설치된 앱에서의 소셜 로그인은 아직 확인하지 않았습니다. 공식 문서가 말하는 길은 둘입니다.

  • 딥 링크로 돌아오기. 앱에 scheme을 등록하고, Redirect URLs에 myapp://**를 넣습니다. 브라우저에서 로그인을 마친 사람이 그 주소로 앱에 돌아옵니다.
  • 네이티브 SDK로 ID 토큰 받기. Google은 @react-native-google-signin/google-signin으로 받은 토큰을 signInWithIdToken에 넘깁니다. 카카오는 OpenID Connect를 켜고 openid 범위로 받은 ID 토큰을 같은 함수에 넘깁니다.

내보내기 전에 볼 것

  1. 제품의 주소에서 카카오와 Google로 각각 처음 로그인해 봅니다. 동의 화면에 제품의 이름이 뜨는지 봅니다.
  2. 로그인을 마친 뒤 제품의 주소로 돌아오는지 봅니다(Site URL이 아닌 다른 곳에 떨어지면 4번).
  3. 테스트 사용자로 넣지 않은 Google 계정으로 로그인해 봅니다(In production인지).
  4. 새 계정으로 가입해 다른 계정의 데이터가 보이지 않는지 봅니다. 정책은 마이그레이션에 들어 있지만, 내보내는 곳에서 한 번 더 봅니다.
