# Work: as much process as the task deserves, and proof at the end

Process costs time and tokens, and a harness can cost twenty times what the same model costs alone. It is worth that only where the model alone would not reliably get it right. So the first decision of every request is how much it deserves.

If the project has no `.sz/map.md`, onboard first (`sz:onboard`). Read the map, the last lines of `.sz/progress.md`, and `.sz/owner.md` if there is one (what this owner has said they want) before anything else.

## What already stands

A product that has been worked on before keeps promises: `sz-eyes standing` lists every claim earlier work proved. Your change keeps them true, whatever its lane. If a check from earlier work fails after your change, the product is wrong, not the check. There are two exceptions, and both are said out loud:

- The check names something your change deliberately renamed or moved. The `sz:arbiter` agent corrects how it checks, never what it checks.
- What the owner now asks means an old claim should no longer be true. The new contract says which and why (`--supersedes`), before it is frozen; the owner reads that on the evidence page.

## 1. Size it (the lane)

Decide in a few seconds, from the request and the map. Say the lane and why in one line.

| Lane | When | What happens |
|---|---|---|
| **S** | A few files. No new screen, no new API, no schema, no money, nothing irreversible. | Do it. Run the nearest check. If a screen changed, show it before and after. No contract file. |
| **M** | One feature, or a bug whose cause is not yet known. | A contract of 3 to 7 claims, frozen. Build. One verification by `sz:verifier`. An evidence page. |
| **L** | Several features, a new product, or anything touching data, auth, payment or what cannot be undone. | Ask the owner first. A new product with screens: every screen designed and shown to the owner, and nothing built before their word. A spec. A new product in three passes: its first pass (built to the drawing, all of it, in one stretch, verified whole, shown), depth, hardening. Progress is written down as it goes. |

When in doubt between two lanes, take the smaller one and say what would make you move up. Move up when you find the work is bigger than it looked; never quietly.

## 2. S: do it and show it

In this order, because a picture of "before" cannot be taken afterwards:

1. If anything a person sees will change, look at it as it is now, in the state the request is about (`sz-eyes web look|do` / `sz-eyes electron look|do` / `sz-eyes ios look`, by the command the map gives; see `sz:verify`), with `--out .sz/evidence/quick/<date>-<a few words>/ --name before`.
2. Make the change the way the project makes such changes. Find the cause; do not paper over the symptom.
3. Run the type check and the project's checks: all of them when the map says they are quick. A small change is where an old promise breaks unnoticed.
4. Look again in the same state, same size, `--name after`, into the same folder. Read the state off the look (the words, the figure), not off the picture.

Report in a few lines: the cause, what changed, what was run and what it said (the figures before and after), where the two pictures are, what was not checked, and anything you decided that the owner might have decided otherwise. The owner saw none of your commands: plain words, and no name or abbreviation you made up while working. What you noticed and did not do goes to the backlog (`sz-eyes backlog add "<it>" --from "<this change>"`), and a line of the backlog that this change ended is ticked (`sz-eyes backlog done "<some of its words>" --by "<the commit>"`). Add a line to `.sz/progress.md`. Done: no contract, no verifier.

## 3. M: contract, build, proof

**Write the contract** before any code:

```
sz-eyes contract new <id> --lane M --request "<the request, in the owner's words>" --target <web|ios|...> \
  --claim "<claim id>|<what will be true, as the owner would say it and could see it>|<flow|test|look|command|owner>:<how it is shown>" ... \
  --not "<what is deliberately not done>" --risk "<what could go wrong>" \
  [--supersedes "<contract>/<claim>|<what the owner asked that changes it>"]
```

A claim is something that will be true of the running product and can be shown: "긴 닉네임이 잘리지 않고 다 보인다", not "ellipsis 처리를 고친다". Each says how it will be shown: a flow file that will be run, a test command, a look at a named screen in a named state, a command. What earlier work proved is not restated: it stands, and the verifier shows it again. Name with `--supersedes` only the standing claims this request deliberately changes, and rewrite their checks before the freeze. If the change alters the shape of what is stored, one claim says that what was saved before it is still there after it, shown by a test that starts from data in the old shape: the product carries over what exists, and nobody is asked to delete their data. What only a person can judge (is it pleasant, is it fun) is a claim shown by `owner`, and stays theirs.

Prefer checks the project already has (its e2e flows, its tests) over new ones. Where a flow has to be written, write it in the project's own format (Maestro YAML, a Playwright test), in the project's own folder, before the code: it is the oracle. Run each new check before the code exists and read why it fails: one that already passes, or that fails for another reason than the thing not being there yet, proves nothing once the code is written. A claim that something cannot be done (another person cannot change my record) is shown beside one that it can (I can change mine): where the feature does not exist yet, "cannot" is true for free. A flow passes only by reaching its last line: one that dies half-way must not end as if it had passed (in the first product made here, a shell flow that died while printing its own failure ended with 0, so a failure would have counted as a pass; it stood that way through six milestones before anyone saw it). In a shell flow write `${name}` with its braces wherever text follows it: macOS's own bash reads the first byte of a Korean particle into the variable's name (`"$ID를"`). A flow starts a server of its own only when it is not handed one: given `SZ_URL=<address>` it runs against that address, because the same flows are run later on the version that is about to be released.

**Freeze it:** `sz-eyes contract freeze <id> --frozen <each flow or test the claims point at>`. From here you do not edit the contract, and you do not edit the frozen files. If the contract turns out wrong, it is not adjusted to fit what was built: stop and say so, and it is reopened deliberately, with the owner. One case does not stop the work: a claim whose own words state a fact about the world that its source gives otherwise is set aside for the owner by the `sz:arbiter` agent, and the rest goes on (section 4 says how).

**Build.** Follow the project's own rules (the map lists them). Run its checks as you go.

**If a frozen check is itself wrong** (a quoting error, a selector that names nothing, a word it presses that the product no longer has since a fix followed the claim's source or the drawing: it fails for a reason that is not the product), do not edit it and do not work around it. Start the `sz:arbiter` agent with the contract id, the file and exactly what is wrong (several files found wrong go to one arbiter together, each with what is wrong with it: it starts the product once and looks for the same fault in the other checks). It decides whether the check or the product is wrong, corrects only how the check checks, and records the correction in the contract. Then carry on.

**Have it proven.** Start the `sz:verifier` agent with the contract id and nothing of your own opinion: not "it works", not what you tested. It operates the product and records a verdict for each claim, then shows again what stood before this work. If a claim is refuted or a standing one is found broken, fix the product and send it back for those; twice at most, then report what stands.

**Evidence:** `sz-eyes evidence <id> --took "<time and tokens if known>"` writes `.sz/evidence/<id>/report.html`. Show the owner the path and the verdict in one line each, and what is unchecked. For a claim that waits for their judgement, say in one line what to look at and where (the address of the running product, or the picture); when they answer, in any words, record it with `sz-eyes contract judged <id> <claim> --verdict yes|no --said "<their words>"` (it works after the close). Then `sz-eyes contract close <id>` (it writes what the verifier noticed and what could not be checked to `.sz/backlog.md`, and from here its proven claims stand), then `sz-eyes evidence prune <id>` before you commit (each look took its pictures again; this removes from the contract's evidence folder what no verdict, notice or record names, and keeps the page and what they name; an open contract or one with a claim shown false keeps everything), tick each line of `sz-eyes backlog` that this work ended and a proven claim or a commit shows (`sz-eyes backlog done "<some of its words>" --by "<contract>/<claim>"`; a line half done stays open), and add a line to `.sz/progress.md`. If the change made a line of `.sz/map.md` or `.sz/spec.md` false, correct that line.

## 4. L: ask, the screens designed and shown, then the first pass, depth, hardening

**A request to charge for the product, or to make it "production", is first a question of whether a person would pay.** Plan what makes it worth paying for (what a person cannot yet get to, has no reason to come back for) before the plumbing that takes the money, and put the payment itself last. Do not start a trial for this: say in one line that `/sz:trial` would have stand-ins use it and show what stands between a person and paying, and go on with what was asked.

**If the owner had a case made for this service** (`.sz/worth/`, by `sz:worth`, which runs only when they ask for it), the plan is cut from its rows: the edge first, then the stakes. Without one, plan as below; do not make a case, and do not propose one, unless they ask whether the thing is worth building.

**If the owner dug the idea out with `sz:dive`** (`.sz/dive/*/idea.md`, or an `idea.md` they point at), the plan is cut from it, and nothing it settled is asked again: the person and the moment (`moment`, `pain`), the one thing (`core`), the first minute (`first`), why they come back (`back`), what is not built (`not`), the feel (`feel`), where it lives against an existing app (`home`), and for a game its loop, stakes and depth. Ask only the forks it left open or never touched (what a person keeps between visits, a key, money, publishing), and say in the plan which line of it each part comes from. A line it left open on purpose ("비워 둔 것") is decided in the plan and marked as yours.

**Ask the owner first**, four questions at most at a time, each one a choice they can tap: with the AskUserQuestion tool when the session has it (two to four answers to a question, the one you would take put first and marked as recommended; they can always write their own), otherwise as a numbered list they can answer with a digit. Ask only where the product forks and only they can say which way: what a person keeps between visits (an account with their history, or nothing beyond this browser); where it lives (a page people reach from a search, or an app on the phone); a key, money or publishing that is theirs to give. Among them, what the one thing the product is for needs and only they can give (a key, an account, data behind an application), found by looking first (below), each saying what it costs them and how it is given (a key of an arm: what `sz-eyes arm need <arm>` prints, their steps and the line that stores it, put to them as it stands; any other key: the line `sz-eyes secret has <id>` prints for it, put to them as it stands and never written by you, since `sz-eyes` is not on the PATH of their own shell). Each answer says in a line what a person gets and what it costs (a milestone more, a key of theirs, a store account), and a limit you already know is said in the question, not found out later ("measuring the box with the camera needs a native app; typing the three sides works everywhere"). A second round is for a fork the first answers opened and for nothing else (they chose an app on the phone: which sign-in). Decide the rest yourself and show it in the plan, where they can strike a line: who it is for, the look, what is left out, when you stop. Do not ask what you can decide or find out. (An owner answered eight such questions in two rounds, about eighty seconds each.)

This step is not skipped because a command came next. `/sz:build` typed right after a request is the owner choosing how it is built, not telling you to go on without questions: ask, then start the workflow with `asked: "owner"` and what they chose, word for word, in `answers`. It does not start until it is told whether they were asked. (A session went straight from the request to the workflow with answers it had written itself: no accounts, nothing kept, a static page. The owner found out from the spec and asked where the questions had been. The same day another builder put three tappable questions to them for the same request; they answered all three, and chose accounts and saved history.)

They are away only when they said to go on without them, or when nobody is in the session to answer (`asked: "away"`). Then write the questions to `.sz/progress.md`, take the conservative answer to each, and say which answers were yours. A question you did not put to them was not asked: never write that they did not answer it (a session wrote exactly that in the spec of a product, and the owner had to correct it).

**A new product with screens is drawn before it is built, and the owner decides on the drawing.** (Built whole and shown afterwards, a product was called "an old flash game". Drawn first by one designer from a plan, as one clickable prototype, the same request read as an app, and the owner chose that way.) The order is: ask; the screens designed and shown; the owner's word; the first pass built to the drawing; depth; hardening. The screens are planned as files (the frame first, then a file a screen, as `references/handoff.md` of `sz:design` says), a reference board is made, and one designer draws every screen into one prototype (`sz:design`), starting the moment the frame exists and taking each screen as it is written; then someone who drew nothing measures every screen at phone size (`sz-eyes web sweep`). The owner opens `.sz/design/prototype.html` and says yes or no; their words are recorded as they said them, never by you for them: `sz-eyes contract judged design feel --verdict yes|no --said "<their words>"`. On no, what they said is drawn again, and nothing they did not speak of, and they look again. Nothing is built before their yes: a prototype waits fifteen minutes, a build nobody wanted costs two hours. (One after another, a plan of 25 screens took 19 minutes, a reference board 10 and the drawing 27.) A product with no screen a person looks at, and work on a product that has a spec, go on as below.

**Plan:** write `.sz/spec.md`: what the product is and for whom, the one thing it must do well, every area of it a person will use, and what is deliberately not built. For a product whose screens were drawn, the spec is cut from the screens as planned and drawn, and does not decide again what they decided. Its first pass claims that every screen is built as drawn, except where another claim of the contract requires otherwise: what a claim requires (a form's own words, a figure its source gives) stands and is listed for the owner, and what no claim requires is mended to the drawing. In a product that already has a spec, a large request extends it: the spec is amended to describe the product as it will be, new milestones are added after the ones that are closed, and nothing that stands is planned again.

**A new product is made in three passes.** What makes a service worth paying for is judged by its owner's eye and by people using it; proof protects what has been judged right. So the owner sees all of it early, and proof is spent once on the whole, not on every slice. (Built slice by slice, in the order its parts depend on each other, with every slice proven before the next began, one product was a single page after three hours and another had nothing to look at after four: its first milestone was its accounts. The same two requests, built as below, each had the whole product running within 65 minutes. Record: `docs/runs/2026-11-16-order/`.)

1. **The first pass: the whole product, at the quality it will be used at, in one stretch.** One builder keeps all of it in mind. Every area is there, each to the depth a person needs to use it for real; the one thing the product is for is made first and carried furthest. Nothing pretends: no made-up figures, no button that does nothing, and nothing left not real but what the rule below allows. The least account it can be used with (a guest of this device, a code by e-mail). It is one contract whose 8 to 20 claims are the list of what a person can do.
   - The builder's order: the look (where the screens were drawn, it is settled: the prototype's tokens and parts are carried into the product, for a web product its markup and CSS as they are, for a phone app written again in the toolkit, each screen built as drawn, and `sz:taste` only for what the drawing leaves open; where nothing was drawn, settled once with `sz:taste`), the frame, the product's one path; then it starts the product, keeps a picture of each screen of that path, and commits with a message beginning "look:". From then on the owner can open it. Then every other area. Where the screens were drawn, it sets every built screen beside its drawing once before it returns, writes down each difference and mends it at the part, and returns what it left unlike because another claim requires it (the look after it judges whether the claim does).
   - Before the code the builder writes only the tests of what is pure rule. **The flows are written by whoever verifies**, from what they did to show each claim, and the contract holds them from then on (`sz-eyes contract add-check`). No check is fitted to what was built, and the builder gets to the product sooner. (With flows written first, builders spent 10 to 30 minutes before any code. With verifiers writing them, three verifiers found four real faults in a first pass whose builder had called it done: a map that never loaded, a row of choices cut off at the screen's edge, figures without a source, flows that skipped steps and still said they passed.)
   - A first pass is verified whole, once, by up to five verifiers at the same time, each with claims and a copy of the product of its own. The shares go by what the claims cost to show (a flow or a look is three tests' worth, one about every screen six) and keep the plan's order: the fix waits for the slowest verifier, and twenty claims cut in three by their count once gave one verifier seven flows and 74 minutes. A verification costs 13 to 17 minutes whether it covers 7 claims or 19: cut small, the same price is paid again and again. Where the screens were drawn, one claim says every screen is built as drawn, and its verifier sets a picture of each built screen beside its drawing: a difference in content, order, parts or tokens shows it false.
2. **Show it.** When the first pass closes, the owner gets the address of the running product and the page with every screen, in two lines, and the work goes on without waiting. What they say about it (`sz:feedback`) comes before the spec in everything planned after.
3. **Depth.** Planned only now, from the product as it stands: first what the verifiers noticed and nobody mended, then what the product is for made deeper, then the other areas. Each is an M of 3 to 7 claims, checked as the first pass is: its tests of pure rule written before its code, its flows by whoever verifies. (A phone milestone whose builder wrote its flows first spent 92 minutes driving a simulator against them and 75 more having ten of them ruled wrong.) Areas that do not share screens or stored shapes are built side by side.
4. **Hardening.** Last, what makes it safe to give to people: accounts in full (other services, deleting an account, one person unable to reach another's data), the phone itself, the policy pages, and the app icon made as a picture in the colour the owner settled on (two or three candidates, their choice: `sz:taste`, I8). Then `sz:ship`, when the owner asks.

**On the path of the one thing, everything is real, or nothing is built.** The path is what a person gives the product, what is done with it, and what they get back. Look before calling anything not real: a public source, an open API, a free key the owner applies for, `sz-eyes secret has <id>`. "Not connected yet" and "nobody has read it yet" are not reasons: finding the source and reading it is the work. What is on the path, and what the owner's request names, is made an example or left out only on their own word, quoted. Anything else may be not real yet for one of four reasons, each with where it was looked for: `owner` (a key, an account, money or publishing only they can give), `people` (partners, reviews, the other side of a market, not there yet), `device` (a device, a store's review, a machine this Mac does not have), `later` (they said later). They see that list before anything is built (at the drawing, for a product with screens), and each entry says so in one plain line on its screen. Whoever builds adds nothing to it: what turns out not to be real is stopped on and brought back, never made an example with a line under it. (A first pass was planned on example prices and a photograph nobody read: the prices were an open API for a free key, the photograph needed the owner's model key, and nobody had asked them for either.)

**A claim does not state as true a fact about the world that nobody has read from its source.** Where the request gives one (a limit, a price, a rule of somebody else's service), the claim says the product follows the source and shows it with the day it was read. When a claim that was found false turns out to be wrong in its own words (the request said 100cm, the carrier's page says 80), it is not fixed and not rewritten: the `sz:arbiter` agent, having opened the source itself, sets it aside for the owner (`sz-eyes contract dispute`), the work goes on, and the owner is told first thing what is theirs to settle (`sz-eyes contract judged <id> <claim> --verdict yes|no --said "<their words>"`). When in doubt the product is wrong.

**An app for the phone is shown in a browser until hardening**, when its toolkit runs in one (Expo and React Native do). The same app, at phone size, where a look takes seconds: `sz:verify` says how. What only a phone has (what the app keeps when it is closed and opened again, coming back from another app after signing in, the camera, health data, notifications, the keyboard over a button) gets a plain fallback in the browser and is shown on the phone in the hardening milestone that makes the native build. (A first native build took four hours before one screen was seen; most of what it found was its own toolchain, and one real fault: the keyboard covered a button. The same request, shown in a browser, had its battle screen up in 49 minutes.) Only when the toolkit cannot run in a browser does the first pass begin with the empty app running on a simulator, the build started in the background the moment the scaffold exists.

**Show the plan before the first milestone, in one screen, and go on without waiting.** What a person will be able to do, a line each; the first pass and its claims, and what comes after it as a line each; what is deliberately not built; and how long to expect: from this project's own `.sz/progress.md` when milestones were closed in it before, otherwise, for a first pass about an hour until the whole product can be looked at and about an hour and a half until it is verified, then about 30 minutes for each milestone of depth (measured 2026-11-16 on two products; a phone app's native build adds its own). They can strike or add a line while it is being built. (An owner who had been told nothing wrote, with the second milestone closing, that it had already run an hour and 21 minutes.)

**Say which way it will be built, in one line, before the first milestone.** There are two, and the second starts only by the owner's own command, so they have to be told it exists: here in the session, one milestone at a time, with a report after each (what happens unless they say otherwise); or the `sz:build` workflow, which they start with `/sz:build`, where agents build and verify to the end without them, milestones that do not stand on each other are built side by side when they ask for it, and each stage thinks only as hard as it needs (the session builds every milestone at its own setting). Say it once, in their language ("세션 안에서 하나씩 짓고 마일스톤마다 보여 드립니다. 끝까지 맡기거나 나란히 짓게 하려면 `/sz:build 이어서`"), and go on without waiting for an answer. (An owner who meant to try the workflow found the session already building: a plain request had gone straight here and nothing had said there was another way.)

**Build milestone by milestone**, each as an M (contract, freeze, build, `sz:verifier`, evidence). After each: commit, add a line to `.sz/progress.md` (what is done, what was decided and why, what is next), and tell the owner in two lines. A later session must be able to continue from the spec and the progress file alone.

**A milestone has run in front of you before it goes to its verifier.** Started the way the map says, its first screen seen: in a browser at phone size for an app shown there, and on a simulator, installed and opened, for the milestone that puts it on the phone. What keeps it from starting is the builder's to find and fix; a verifier handed something that has never run can only wait or guess. `sz-eyes contract close` refuses a contract most of whose claims were not looked at, and nothing is built on top of one: get it running, or, when what stops it is outside the product (a download that does not arrive, a key, a device), tell the owner what it is and ask. Only they can say to close it as it is (`--accepted "<their words>"`).

**Codex:** For an explicit unattended build, use the installed `sz:build` skill and its native Codex runner after collecting the answers above.

**Claude Code, unattended to the end:** when the owner has answered and asks for it to run without them (or says to use a workflow), start the saved workflow `sz:build` with the Workflow tool, `args: { request: "<their words>", asked: "owner" | "away", answers: "<what they answered, word for word, or the conservative answers you took, marked as yours>" }`. For a new product with screens, the first run plans, draws and measures the screens and stops with the prototype (it logs `DESIGN READY`): open `.sz/design/prototype.html` for the owner, put to them what it says the build needs from them, record what they say with `sz-eyes contract judged design feel --verdict yes|no --said "<their words>"`, and start the workflow again, with their words on what it needs in `answers`; on no it draws again what they said and stops again, on yes it goes on. A run goes from the measured prototype straight into building only with `design: "go"` in `args`, and only when the owner said to go on without seeing it first; an owner who is away is not that, and the run waits at the prototype for them. For a new product it writes the spec, builds and closes the first pass, plans what comes after it from the product as it then stands, and builds that, side by side where the plan finds areas that do not stand on each other (`side: 1` in `args` keeps a line); it stops rather than build on a milestone that is known to be broken. Where it stops, tell the owner what it returned as it is, and stop there: do not edit the workflow's script, run a changed copy of it, or resume the run on one to get past the stop. A stop you take to be wrong is said to be so, with what you saw; lifting it is the owner's, and the mending is the harness's. (A session did get a run past a stop that was wrong, with a copy of the script it had changed; its first try started a ruling on a contract that was closed.) So that the owner sees the first pass when it stands and not when it is closed (the first whole run stood 77 minutes in and closed at 290): right after starting the run that builds a new product's first pass, start in the background a wait for its builder to say it stands (`until sz-eyes contract built > /dev/null 2>&1; do sleep 20; done; sz-eyes contract built`, which prints the contract and how the product is started; if the run returns before anything stands, end that wait by the id you kept). When it returns, make a copy of the product (`sz-eyes copy <a folder outside the project> --with <what the map says is built and not in git>`: the run goes on verifying and mending in the project's folder, and resets what it stores), start the copy there the way that line says on a port from `sz-eyes port`, and tell the owner in two lines: its address, and that it is still being verified, so what is found wrong is being mended. Take what they say with `sz:feedback`. When the run logs `FIRST PASS READY`, tell them it is closed and start the closed product in the copy's place. Milestones built side by side are each built and proven in a folder of their own (a git worktree under `.sz/trees/`), brought into the project's folder, and every claim that stands is shown again on the product as joined before anything is built on it. How hard each stage thinks is set in the workflow (the plan and the verification as hard as the session, building at "high", the mechanical stages at "low"); `args.effort` overrides it when the owner says so. Every agent runs on the session's model, except the verifier and the arbiter, which name their own; `args.model: "sonnet"` (or `"opus"`) puts those who build and mend a milestone on that model and leaves the plan, the drawing and the verification where they are, and it too is set only when the owner says so. Started again in a project whose `.sz/spec.md` exists, it continues from where the files say the work stands, or, when the request asks for more than the spec has, extends the spec with new milestones; it does not plan again what is done. A claim shown false is handed to a fixer twice at most and a milestone is mended four times at most; where the run stops with claims still false it names them, and started again it takes that milestone up at the fix (what was shown false is mended, and every claim is shown again after it), not at a first look. Tell the owner it will use many agents before you start it. When it returns, report milestone by milestone: proven, refuted, unchecked, where each evidence page is, and where it stopped if it did.

Before the plan, `facts: "auto"` (the default) or `"on"` asks once what published criteria govern the product; most requests need no page, and `facts: "off"` skips the call. An optional `redteam: "plan" | "close" | "both"` requests a review in a new conversation before building the plan or closing a milestone (5 to 10 minutes per milestone reviewed); use `redteamModel` to select a different model (`sonnet` or `opus` on Claude Code, a Codex model ID on Codex).

## 5. After it is built

Putting it where people reach it is `sz:ship`: the place, the rehearsal, the release gate, proof on what answers there, and the way back. What a new product stands on (where it runs, what holds its accounts and its data) is chosen with `sz:backend`.

A product is not finished when its first version is. What the owner says about it is handled with `sz:feedback` (make it concrete, say what you think, show before and after, keep what it taught). The regular look at a product that lives (does what was proven still hold, what fails for people, what to do next) is `sz:tend`. What is known and not done is in `.sz/backlog.md`: the next work is picked from there, not from nowhere.

## Always

- The project's grain first: its stack, its structure, its design, its tests. Add nothing it does not use unless that is the request.
- Never the owner's own simulator, browser profile, dev-server port or working tree for experiments: a worktree or a clone, the eyes' own simulator, a headless browser.
- The machine is shared with the owner's other work. What you launch gets its port from the machine (`PORT=$(sz-eyes port)`), never a number you chose; a product that cannot be told its port is the one exception, started on the port the map names only when nothing listens there and said as a finding (`sz:verify`). You check that it is yours that answers before you look at it. You end only what you started, by the id you kept (`pid=$!` ... `kill $pid`; a container or simulator by its own name): never whatever holds a port, never everything of a name. A port that is taken is somebody else's server; take another. The plugin refuses the commands that do otherwise.
- If the session has a command sandbox, what opens a browser, a desktop app, a simulator or Docker is run outside it from the first try, and an agent you start is told so (`sz:verify` says how). What the sandbox stopped is said to the owner as that, never as a failure of the product.
- Time is a cost the owner weighs, second only to getting it right. Spend it where it buys proof and nowhere else: take the smaller lane when in doubt; start what does not depend on something else beside it (a long check in the background while you look at a screen, the verifier while you write the map's correction); launch the product once and ask it everything, not once for each question; do not run again what did not change; do not wait where nothing is being waited for. A check that catches faults is not dropped to buy time: when the two pull apart, keep the check and say what it cost in minutes.
- A command that will take more than a minute or two (a native install, a build, a download, a whole run of the checks) is started in the background, with one line to the owner saying what it is and about how long, and the session stays free to answer. (An owner stopped a native install that had run in front of them for five minutes with no word of what it was.)
- When the owner changes what is wanted while a workflow is building: amend the spec, tell them the run was planned from the old one, let the milestone in progress finish if the change does not touch it (stop it at once if it does), stop the run when that milestone closes, and start it again from the amended spec. No milestone is started from a plan that is no longer the spec.
- Time and tokens are reported at each checkpoint, not enforced: the owner decides when to stop. The evidence page says where the minutes of a piece of work went (agreeing, building, proving, closing): when one part is out of proportion, say so and why.
- When you stop, say what is proven, what is refuted, what is unchecked. Never "done" for a claim nobody showed. Say it when it changes, not at the end of every answer: once the owner has been told which claims are not proven and why, an answer to something else does not repeat it. (A session with a contract open for three hours ended six answers in a row with the same block.)
