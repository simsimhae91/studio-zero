# Studio Zero

서비스를 만들고, 만든 것이 약속대로 됐는지를 **만들지 않은 쪽이 돌아가는 제품에서 증명하고**, 한 장으로 보여 주는 하네스. 그리고 그 앞뒤: 지을 만한 서비스인지 세상의 증거로 따지고, 내놓은 뒤에는 증명한 것을 지키면서 고치고 키운다.

이 저장소에는 두 가지가 들어 있다.

| | 무엇 | 지금 |
|---|---|---|
| **`plugin/` + `packages/eyes`** | Claude Code 위의 하네스(`sz` 플러그인)와 그 눈·손(`sz-eyes`) | **지금 쓰는 것.** 새 일은 전부 여기에 들어간다 |
| `packages/daemon` + `apps/desktop` | 처음의 스튜디오: 엔진을 컨테이너에 넣어 돌리는 데몬과 Tauri 앱 | 그대로 돌아간다. 새 기능은 더하지 않는다 |

## 왜 이렇게 되었나

처음의 스튜디오는 "엔진을 믿지 말고, 가두고, 관문으로 막는다"는 전제 위에 있었다. 1년 동안 그 위에 걷기, 화면 측정, 디자인 핸드북, 제품 지도가 쌓였다. 아래는 그 전제가 어디서 틀렸고 무엇으로 바뀌었는지다. 날짜마다 본 것과 정한 것을 적는다. 자세한 근거는 끝의 기록에 있다.

**1. 가둔 엔진의 천장은 맨 도구보다 낮았다 (2026-11-15).**
들여온 네이티브 앱 하나를 스튜디오가 다루게 하는 데 27분과 191만 토큰이 들었고, 그러고도 볼 수 있는 것은 웹 화면뿐이었다. 같은 날 그 앱이 이미 가진 흐름 하나를 호스트의 iOS 시뮬레이터에서 돌리는 데는 1분 47초, 토큰 0이 들었다. 엔진은 자기 도구를 뺏긴 채 라운드마다 새로 떴고, 남의 제품은 집의 디자인 규칙으로 재어져 "결함" 68건이 나왔다. 가장 센 에이전트를 약하게 만드는 우리에서는 차이가 나오지 않는다. 그래서 스튜디오를 Claude Code 위로 옮겨 앉혔다. 작업 공간·세션·병렬·재개는 플랫폼의 것을 쓰고, 맨 도구에 없는 넷만 짓는다.

| 짓는 것 | 무엇 |
|---|---|
| 계약 | 일을 시작하기 전에 "무엇이 참이 되고 무엇으로 보일 것인가"를 적어 얼린다. 일의 크기만큼만 |
| 눈과 손 | 웹, iOS 시뮬레이터, Electron 앱, 웹 게임을 띄워서 보고 누른다 |
| 검증자 | 만들지 않은, 깨끗한 맥락의 에이전트가 계약을 하나씩 증명하거나 반증한다 |
| 증거 | 소유자가 30초에 읽는 한 장 |

**2. 첫 버전이 끝이 아니다 (2026-11-15).**
서비스는 고치고 키우는 동안 망가진다. 그래서 한 번 증명한 약속은 계속 지켜야 할 것으로 남고(뒤의 일은 그것을 깬 채로 닫히지 않는다), 일하다 눈에 띈 것은 남은 일 목록으로 가고, 소유자가 한 말은 그 제품의 규칙으로 남아 다음 일 전에 읽힌다.

**3. 내놓는 일도 약속이다 (2026-11-15).**
에이전트가 만든 서비스의 사고는 정해져 있다: 열린 데이터베이스, 번들에 든 관리자 키, 지워진 운영 데이터. 그래서 출하는 매번 같은 줄을 지나는 관문이다. 내보내기 전의 후보에서 절반, 사람들이 닿는 주소에서 절반을 증명하거나 까닭을 적어 면제한다.

**4. 소유자의 첫 실사용에서 하네스는 그 자리에 없었다 (2026-11-15).**
다른 프로젝트(Electron 앱)에서 47분, 요청 여섯 번 동안 플러그인의 스킬이 한 번도 불리지 않았다. 지도 없는 프로젝트에서 아무 말도 하지 않았고, 데스크톱 앱을 볼 눈이 없었다. 그리고 "돈 받고 싶다"는 말에 세션은 결제 창구부터 지었다. 고친 것: 시킨 일은 하네스의 방식으로 하도록 요청마다 한 줄을 붙이고, Electron 눈을 만들고, 코드를 안 본 대역이 그 제품의 사람이 되어 끝까지 써 보는 단계를 넣었다.

**5. 어떤 서비스를 내놓느냐가 몇 개를 내놓느냐보다 중요하다 (2026-11-16).**
약속대로 지어졌다는 증명은 그것이 지을 만한 것이었는지를 말해 주지 않는다. 그래서 서비스의 근거도 계약처럼 다룬다. 누가, 지금 무엇으로, 이미 돈이 오가는가, 어디서 실망하는가, 갈아탄 적이 있는가, 어디서 만나는가. 세상에 대한 줄은 누구나 열 수 있는 페이지의 문장으로만 보였다고 하고, 그 문장이 그 페이지에 있는지 하네스가 다시 열어 확인한다. 쓰지 않은 에이전트가 인용을 하나씩 읽고 근거를 뒤집어 본다. 깊이는 느낌이 아니라 사람들이 대신 쓰는 것들과의 대조표다(있음, 얕음, 없음, 안 함). 기본값은 "짓지 않는다"다.

처음 돌린 시편에서: 인용 150번 중 34번이 그 페이지에 없는 문장이라 버려졌고, 반박 12개 중 치명적인 하나가 받아들여져 판정은 "좁혀서"였다. 소유자의 눈에 좋아 보이던 제품이 내놓을 서비스는 아니라고 나왔다. 이 단계가 필요했던 까닭이 그것이다.

**6. 모든 것을 말에서 짐작으로 잇지 않는다 (2026-11-16).**
4번의 수리가 반대쪽으로 지나쳤다: 지나가는 말 한마디에 에이전트 여럿이 몇십 분을 쓰는 단계가 시작됐다. 그래서 둘을 나눴다. **시킨 일을 하는 방식**(크기를 재고, 약속을 적고, 만들지 않은 쪽이 증명)은 말에서 그냥 이어진다. **따로 시작되는 단계**(써 보기, 지을 만한가, 출하, 돌봄, 끝까지 빌드)는 명령이나 그 일을 콕 집어 시킨 말에만 시작한다. "지을 만한가"는 만들기 전에 거치는 단계가 아니고, 물을 때만 돈다.

**7. 전체를 먼저 짓고, 전체를 한 번 검증한다 (2026-11-16).**
소유자가 같은 날 직접 돌린 두 번: 택배 비교 서비스는 3시간 뒤 한 페이지였고(약속 28개 증명, 반박 0), 다이어트 배틀 앱은 4시간 뒤에도 볼 것이 없었다(첫 마일스톤이 네이티브 빌드 위의 계정이었다). 조각마다 다 증명하고서야 다음 조각을 짓는 순서에서는 소유자의 눈이 맨 끝에 온다. 그런데 서비스가 돈 낼 만한지를 정하는 것이 그 눈이다. 그날 밤 같은 두 요청을 과정만 바꿔 여섯 번 돌렸고, 사례를 읽었다(방법론들, 앱을 통째로 짓는 제품들, 에이전트를 몇 시간씩 돌리는 팀들). 숫자와 사례가 같은 쪽을 가리켰다.

| | 전의 과정 (소유자의 실행) | 새 과정 |
|---|---|---|
| 택배 비교 | 181분, 한 페이지 | 50~64분에 전체가 서고, 100분에 약속 19개 중 18개 증명 |
| 다이어트 배틀 | 4시간, 볼 것 없음 | 49분에 대결 화면, 63분에 전체 |

그래서 새 제품은 세 번에 걸쳐 만든다. **첫 판**: 빌더 하나가 제품 전체를 쓸 수 있는 품질로 한 번에 짓는다(제품의 핵심 줄기부터, 꾸며낸 것 없이, 계정은 최소로). 화면 검사는 만든 쪽이 아니라 검증하는 쪽이 쓰고, 전체를 검증자 셋이 한 번에 본다. 첫 판이 닫히면 바로 보여 준다. **깊이**: 서 있는 제품을 보고 계획해, 서로 기대지 않는 영역은 나란히 짓는다. **굳히기**: 계정 전부, 폰 그 자체, 약관은 마지막에. 폰 앱은 브라우저에서도 도는 도구로 만들면 굳히기 전까지 브라우저에서 폰 크기로 본다. 약속의 문구가 세상의 사실과 다른 것으로 드러나면(요청은 100cm, 택배사 안내는 80cm) 그 약속은 소유자가 정할 것으로 따로 두고 나머지는 계속 짓는다. 검증은 줄이지 않았다: 조각마다 치르던 값을 전체에 한 번 치른다. 기록: `docs/runs/2026-11-16-order/`, `docs/research/2026-11-16-order-of-work.md`.

**처음부터 바뀌지 않은 것.**
- 됐다는 말은 보여 준 것에만 한다. 증명됨, 반증됨, 확인 못 함을 섞지 않는다.
- 만든 쪽이 자기 일을 채점하지 않는다.
- 근거의 종류를 섞지 않는다: 세상의 글, 소유자가 아는 것, 제품에서 본 것, 대역이 써 본 것, 진짜 사람의 숫자. 대역의 "낸다"는 누가 낸다는 증거가 아니고, 돈을 냈는가는 진짜 돈으로만 말한다.
- 절차는 값이 든다. 일의 크기만큼만 쓰고, 시간을 잰다.
- 소유자만 판단할 수 있는 것(보기 좋은가, 재미있는가, 지을 것인가)은 소유자에게 남긴다.

## 쓰는 법

```bash
cd <프로젝트 폴더>
claude --plugin-dir <이 저장소>/plugin
```

Codex에서도 같은 빌드 워크플로를 실행할 수 있다. 이 저장소에서 `pnpm install`로 의존성을 준비하고 로컬 마켓플레이스를 등록한다.

```sh
codex plugin marketplace add .
codex plugin add sz@studio-zero
```

대상 프로젝트의 Codex 입력창에 `$sz`를 입력하고 목록에서 **build (sz)**를 선택한 뒤 요청을 적는다. 빌드는 단계마다 새 Codex 세션을 열며 기본 모델은 `gpt-6.2-astra`다. 계획·구현은 `high`, 독립 검증·분쟁 판정은 `xhigh`, 마감·병합은 `low`다. 시안 승인과 실패 후 재검증은 Claude와 같은 워크플로가 처리한다. [터미널 실행법과 권한 범위](plugin/README.md#codex에서-빌드)

계속 쓰려면 Claude Code 안에서 `/plugin marketplace add <이 저장소>` 뒤 `/plugin install sz`.

"고쳐 줘", "이 기능 넣어 줘"는 평소처럼 말하면 된다. 지도가 없는 프로젝트면 먼저 지도(`.sz/map.md`)를 쓴다. 아래 표는 Claude Code의 슬래시 명령이다. 명령 뒤에 하고 싶은 말을 붙인다.

| 명령 | 언제 | 걸리는 것 |
|---|---|---|
| `/sz:build <만들 것>` | 새 제품, 또는 기능 여러 개를 끝까지 | 워크플로. 시작 전에 선택지로 몇 가지만 묻는다. 새 제품은 첫 판(전체)을 한 시간쯤에 세우고, 검증한 뒤 깊이와 굳히기로 간다 |
| `/sz:work <요청>` | 고치기, 기능 하나 (말로만 해도 같다) | 작은 수정은 몇 분, 기능 하나는 5~10분 |
| `/sz:feedback` | 제품을 둘러보며 말하기, 보고 느낀 것 말하기 | 창이 뜬다 |
| `/sz:trial` | 사용자 대역이 끝까지 써 보기 | 대역 3명, 5분 안팎부터 |
| `/sz:worth` | 지을 만한가, 돈 낼 만한가, 얼마나 깊은가 | 웹 조사와 반박, 20~45분 |
| `/sz:ship` | 출하 | 계정·돈·첫 공개는 먼저 묻는다 |
| `/sz:tend` | 제품 점검, 다음에 할 것 | 10분 안팎부터 |
| `/sz:onboard` | 하던 프로젝트 파악 (지도 쓰기) | 몇 분, 코드는 안 건드린다 |

프로젝트에 생기는 것은 `.sz/` 폴더 하나다: 지도, 계약, 증거 페이지, 지켜야 할 약속, 남은 일, 소유자가 한 말, 써 본 기록, 근거. 전부 파일과 HTML이라 앱 없이 열린다. 소유자용 안내는 [plugin/README.md](plugin/README.md).

## 증명된 것과 아닌 것

실제로 돌려 본 것 (소유자의 Claude 구독, 시편 제품에서. 기록은 `docs/runs/`):

- 기능 하나: 지도 → 계약 → 구현 → 검증자 → 증거. 같은 요청이 속도 개선 전 9분 17초, 뒤 4분 41초 (한 번씩).
- 새 제품을 마일스톤 세 개로 끝까지: 계정이 있는 제품(Worker + D1), 증명 19, 반증 0.
- 출하 관문을 이 Mac의 컨테이너에 두 번. 공개 배포는 아니다.
- 써 보기: 웹과 Electron. 스킬 이름 없는 요청에서 스스로 붙었고, 대역 셋이 며칠치를 썼다.
- 지을 만한가: 한국의 공개 페이지에서 인용을 모으고 기계로 확인하고 반박까지.
- 지나가는 말에는 단계가 시작되지 않는 것.
- 명령 샌드박스를 켠 채(자동 모드) 빌드 워크플로가 끝까지 도는 것. 같은 마일스톤을 추론 강도만 바꿔 지은 시간(xhigh 21~23분, high 11분, 판정 같음).

아직 아닌 것:

- 공개 배포, 계정이 있는 제품의 출하, 모바일 스토어.
- 브라우저 확장, 실제 게임 빌드, 결제 순간까지 가는 대역.
- 마일스톤을 나란히 짓는 것: 구현되어 있고 청할 때만 켜진다. 실제로 나란히 돈 적은 없다.
- 아무 생각 없이 시작하는 사냥("뭘 만들까"), "짓자"로 끝나는 근거.
- 판정이 맞았는지. 근거가 어디까지 있는지를 말할 뿐이고, 팔리는지는 진짜 사람만 답한다.
- 이 하네스가 만든 서비스가 돈을 번 적은 없다.

|---|---|

## 처음의 스튜디오 (데몬과 Tauri 앱)

코어 데몬이 프로젝트마다 OrbStack 샌드박스를 띄우고 그 안에서 엔진(Claude Code, Codex, Cursor, Antigravity의 구독)에게 일을 시키고, 헤드리스 브라우저로 감사하고, Tauri 앱과 폰 알림으로 보여 준다. 설계 전체와 구현·검증 상태는 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)에 있다.

```bash
pnpm install
pnpm daemon                                       # 제어 127.0.0.1:49200, 게이트웨이 127.0.0.1:49201
pnpm sz status

pnpm --filter @studio-zero/desktop dev            # http://127.0.0.1:1420/?demo 는 데몬 없이 예시 데이터로 열린다
pnpm --filter @studio-zero/desktop tauri build    # Rust 필요

deploy/install-launch-agent.sh                    # 로그인할 때 데몬이 저절로 뜨게
```

필요한 것: macOS, Node.js 24.3 이상, pnpm, [OrbStack](https://orbstack.dev). 상태는 `~/.studio-zero/`에 있다. 키는 `pnpm sz vault set <id>`로 macOS Keychain에 넣는다. 플러그인도 같은 금고를 이름으로 쓴다(`sz-eyes secret`).

## 개발

```bash
pnpm typecheck
pnpm test              # 2026-11-23 전량 실행 기준 624개(602개 통과, 실패 0). 22개는 옵트인이다. Chrome, Docker, 실제 세션이 필요한 것은 없으면 건너뛴다

SZ_TEST_ELECTRON_BIN=<Electron 실행 파일> node --test --test-name-pattern="built on Electron" packages/eyes/test/ship.test.ts
SZ_TEST_REAL_KEYCHAIN=1 pnpm test   # 임시 키체인으로 실제 Keychain 왕복 (옵트인)
SZ_TEST_ENGINE=1 pnpm test          # 실제 OrbStack에서 샌드박스와 게이트웨이 (옵트인)
node apps/desktop/scripts/audit.ts  # 클라이언트 화면을 시각 검사에 통과시킨다 (먼저 클라이언트를 빌드)
```

빌드 단계가 없다. Node 24가 TypeScript를 그대로 실행하고, `plugin/bin/sz-eyes`는 `packages/eyes/src`를 그대로 돌린다. 그래서 플러그인을 읽고 있는 세션이 있을 때 그 파일들을 고치면 그 세션에 바로 닿는다.
